# External dependencies and host obligations

Identity: `seampoint.work-class/1.0.0-draft.3/external-dependencies`. Status: `DRAFT_NOT_ADOPTED`, `APPARATUS_ONLY`.

The work-class contract accepts facts from systems outside the deterministic consumer. These facts are inputs with explicit bindings and failure behavior. They are not inferred from names, credentials, provider reputation or local time.

The dispatch authorization fence row below describes the inherited single-provider `AUTHORIZE_DISPATCH` carrier when the selected operation step omits `dispatch_gate` and elects that carrier. A selected step with `dispatch_gate` follows its gate form and every applicable profile: the `approval_requirement` form in [OBSERVATIONS-AND-DISPATCH.md](OBSERVATIONS-AND-DISPATCH.md), sections 5 through 9, or `SOURCE_REQUIREMENTS` in [INDEPENDENT-HUMAN-DECISIONS.md](INDEPENDENT-HUMAN-DECISIONS.md), LIFE-009B, with [HOLDINGS.md](HOLDINGS.md), [INFORMATION-FLOW.md](INFORMATION-FLOW.md) and [ASSESSMENTS.md](ASSESSMENTS.md) when selected. At native commitment, the declared provider or coordinator atomically validates every row in the selected gate's complete retained source vector and any profile-specific fence row against authoritative current state, enforces the selected effectiveness, withdrawal, validity, expiry and uniqueness conditions, and orders all participating writers with that conditional acceptance. The approval revision in the singular table row cannot replace a declared gate's complete fence.

Both ungated paths, direct dispatch and optional inherited `AUTHORIZE_DISPATCH`, require the four accepted deployment evidence records under LIFE-003 and documentary confirmation that the source and policy permit the finite proposal-authority snapshot in LIFE-008. Accepted record statuses alone do not establish that source meaning. Both paths retain the exact committed permit, LIFE-009 dispatch and consumption rules, and LIFE-010 native-evidence rules. A retained optional authorization also requires LIFE-009A's exact fence and dispatch-digest bindings.

| Distributed coordination | Deployment owner | Provide one serialized writer for each organization-and-instance namespace and for each reservation registry, enforced by an atomic expected-revision comparison before commit. A row lock or serializable transaction on the state row, a conditional write keyed by revision, or a single-partition ordered log each supplies it. For each admitted lifecycle transition, the complete returned work state, any affected state in the single selected reservation registry, and the complete canonical request and response preimages in the event log form one atomic commit unit under LIFE-005, LIFE-008 and LIFE-020. Separate per-root locks, revision checks or conditional writes do not by themselves satisfy that combined commit requirement. No transaction across unrelated work instances is required, and cross-registry atomic proposals remain outside this candidate. A host that cannot confirm the complete commit must not dispatch. A selected dispatch gate separately requires its declared provider or coordinator to order all participating writers with native acceptance; one mediator can supply this boundary where the selected profile permits it, without a general distributed transaction. | Store transaction and fencing evidence bound to organization, instance and state revision | Refuse deployment or transition when coordination is unavailable | Test concurrent deployment, failover, fencing and split-brain behavior | Distributed execution is outside this candidate. |

Each active `CLOSED_DOCUMENTED_BOUNDARY` record binds the exact candidate and pin, affected paragraph and requirement identifiers, one typed responsible party, the required control or integration, evidence format, failure behavior, deployment verification method, what the record establishes, what it does not establish and the residual limitation. Its scopes must agree exactly with the coverage inventory. A boundary record closes the specification's description of what a host must supply. It does not turn a deployment obligation into a semantic qualification result or prove that the external fact is true.
