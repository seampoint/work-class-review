# Shared bounded reservations

Status: `DRAFT_NOT_ADOPTED`, `APPARATUS_ONLY`. This normative candidate document defines the closed shared-reservation profile. Qualification applies only after its schemas, decisive expectations and implementations are frozen and tested. Aggregate evaluation alone does not implement these transitions.

## RES-001. Registry, budget identity and organizational policy

A registry is one explicitly selected host-owned scope for shared exposure. Its immutable configuration has an id, principal, clock source, administration provider, administration role and a sorted inventory of budget slots. Each slot has an anchor and exposure_domain. Both are unique within the registry. The organization assigns every occurrence governed by that exposure domain to this same registry and slot. Authentic selection, completeness of this assignment and prevention of another registry being used to reset exposure are host obligations. The contract does not infer that two differently named business policies mean the same thing.

A shared budget definition contains schema, anchor, exposure_domain, principal, complete aggregate definition, permitted contributor class identifiers and reservation_policy. Its digest kind is budget-definition. The complete aggregate definition fixes reducer, nominal types, units, grouping, window, bound, contribution mappings and history provider/source. This profile requires a nonnegative COUNT, SUM or CARDINALITY, an LT/LTE upper bound, a ROLLING or CALENDAR window, SECOND precision and INCLUDE_ALL_RESERVED. The organization must expressly select INCLUDE_ALL_RESERVED. A definition that excludes unsettled reservations is not a shared-capacity reservation definition under this profile. A zero SUM contribution can qualify mathematically, but an unrelated mapping or false qualifier cannot discharge a required shared-budget anchor.

The reservation policy has a positive permit_seconds, affirmatively authorizes pending exposure across window rollover, explicitly selects blocking of affected partitions and blocking of an anchor when an effect cannot be projected, and names a settlement provider/source and a no-effect provider/source. Permit duration bounds reliance for new dispatch; it never expires the pending charge. Calendar and grouping meanings are AGG's directly stated rules, including pinned tzdb 2025a. Normal calendar windows are supported. Signed netting, business-day calendars, currency conversion, lower-bound reservations and live budget migration are unsupported.

The permitted contributor-class list is an upper bound, not an authorization. A listed class without a separately registered exact authorization cannot reserve capacity. Each exact work-class authorization is a separate complete record with id, budget_digest, work_class, work_class_digest, envelope_digest, principal, operation step and a projection. Projection rows name the native field, its class type, the budget field and its budget type. The mapping is explicit even when two type identifiers have the same spelling. Every projected source field and type exists in the complete class bound by the authorization; scalar kind, unit and nonnegative flag agree with the target type. Every budget field used by any applicable contribution, qualifier or grouping selector is supplied exactly once. No English or field-name similarity creates a mapping. Authorization records are bound to registration separately from the definition to avoid circular hashes.

Registration permanently binds one configured slot to one definition digest. An occupied slot refuses a different digest, even after its outstanding exposure reaches zero. Registering a new definition under another anchor cannot reuse the same configured exposure_domain. Changing the configuration or registry identity is migration and is not an operation in this profile. The host retains old registries and their outstanding exposure when considering a later migration. No attestation silently carries to a changed class, envelope, budget or projection.

## RES-001A. Exclusive keys in the reservation transition

Draft 3 broadens the shared-budget transition role to `RESERVATION_TRANSITIONS`. The same registry and one atomic expected-revision transition may reserve numerical contributions and non-quantitative `EXCLUSIVE_KEY` slots. The configuration may contain an empty numerical `slots` inventory when its `exclusive_slots` inventory is nonempty. Both inventories cannot be empty. An exclusive key has a registry, slot, namespace and typed key value. Its digest excludes the owner so two occurrences that name the same business identity collide. A key is `HELD` while an occurrence is unresolved and `CONSUMED` after an exact native completion. The registry must retain it through safe `NOT_SENT`, expiry and abandonment unless the source explicitly supplies a release rule; the consumer does not invent release.

The provider or one exclusive mediator must guarantee uniqueness across all writers and seed the registry from the provider's existing history before accepting a new key. A local ledger does not establish that guarantee. Authority and principal binding occur before lookup; a registry principal that differs from the authority-envelope principal is `DEPENDENCY_MISMATCH`; a stale registry revision is checked before occupancy. A protected receipt may identify the occupied key for internal reconciliation, but an external response does not disclose the owner or key value. A mismatch, missing, unavailable, ambiguous or conflicting completion holds every affected key and budget. Exact completion consumes the complete key set and settles the corresponding reservation in the same durable transition. Both the attributed native request and the observed native request must equal the complete retained reservation request before a key can be consumed, including in a reservation that also carries numerical budgets. Owner matching compares both instance and occurrence identifiers.

## RES-002. State and receipts

The complete state has schema, specification_pin, core and receipts. Core contains the immutable registry configuration, a natural revision, registered budgets, reservations and effect records. All collections are sorted unique by their declared keys. Each registered budget retains its complete definition, exact class authorizations and full history. A reservation retains its id, occurrence key, original exact authority proposal and envelope digests, projected contributions for every affected budget, creation time, current permit expiry and state OPEN, UNKNOWN, SETTLED, RELEASED or DISPUTED. The complete latest authority input and result are retained for OPEN/UNKNOWN/DISPUTED reservations; they are evidence of the admission that occurred, not reusable permission for a new occurrence.

The occurrence key is digest(reservation-occurrence,{work_class,instance,occurrence}). It uses the stable class identifier, so changing its revision within that same occurrence cannot create another reservation. Reservation id is the first admission event id. One occurrence can be admitted only once. RENEW changes the current receipt for that occurrence; it never creates another operation or a second charge. A different work class or instance still draws from the same registered budget.

Each transition receipt contains the complete event digest, prior state digest, new revision, next core digest, decision, reservation id or null, ordered per-budget aggregate results, retained authority result or null, and reasons. Digest kinds are reservation-state, reservation-core, reservation-event and reservation-receipt. A receipt does not include the full next-state digest, because it is itself retained in that next state. Its next_core_digest identifies the resulting core without a circular reference. The returned state_digest is computed only after appending the receipt.

The input supplies complete state bytes and their digest. State admission recomputes every stored definition, authorization, contribution, occurrence and receipt subject it relies on; checks referential consistency, sorted uniqueness and revision relationships; and rejects impossible state. A correct digest alone does not authenticate state. Protected storage and selection of the latest committed revision are host obligations. A component cannot restore an older state from an untrusted caller and claim to prevent rollback.

## RES-003. Event admission, serialization and replay

The aggregate-step input has schema, specification_pin, complete state, state_digest, event and host_evidence. The complete event has id, expected_revision, kind, clock and its kind-specific payload. Its digest includes its supplied clock, authority input, histories and native records. Host evidence contains exact authenticated administrative/native record digests selected independently by the host; those facts are mechanically bound and retained, not authenticated by hashing.

Admission order is (1) closed shape and canonical embedded bytes; (2) selected candidate, complete state integrity and event dependency bindings; (3) existing event replay; (4) expected revision and monotonic clock; (5) action-specific input integrity and required organizational evidence; (6) policy evaluation and transition. A malformed event is an admission refusal and leaves the supplied state and every reservation unchanged. It does not become a policy refusal merely because the budget would also be exceeded.

Every event id is unique within the registry. An exact replay of an already admitted event returns its established receipt, replay:true and the current state unchanged. It does not roll state back to that receipt's revision or provide another dispatch permission. An altered body under the same id is REPLAY_CONFLICT. An exact replay is recognized before its now-stale expected_revision. A new event with stale expected_revision is REVISION_CONFLICT. The caller must resubmit a new event against fresh state after either conflict; changing the body of an old event id is never a retry.

New events use the registry's explicit clock source and whole-second UTC. An unavailable clock is a policy inability to establish permission for RESERVE/RENEW. A backwards clock is an admission failure. Equal instants are allowed for serialized events. The host serializes all affected budgets under the one expected registry revision. The pure transition receives only one selected state; it does not implement locking itself.

For `RESERVE` and `RENEW`, `event.payload.authority.clock` equals the complete `event.clock` record: `source`, `status` and `instant`. Each source also satisfies its existing envelope or registry binding. For a new event, check this equality first in action-specific input admission, after phases 1 through 4 and before every other phase-5 check, authority evaluation or unavailable-clock withholding. A mismatch is `DEPENDENCY_MISMATCH`, leaves the complete state unchanged and creates no receipt. Earlier shape, state, replay, expected-revision and registry-clock admission rules retain their precedence. Matching `UNAVAILABLE` records do not establish permission; the existing integrity checks and unavailable-clock withholding rules still apply.

Every valid policy decision produces one receipt and advances the core revision exactly once, including a withheld reservation. A refusal to admit input creates no receipt and advances nothing. All affected budget histories, contributions and reservations commit together. A later partition violation leaves every reservation unchanged; the complete refusal receipt may still be committed. The consumer prepares all changes before constructing a successful next state.

## RES-004. Full revisioned history

Explicitly selected recovery adds the disposition, contingent-exposure and policy rules in [RECOVERY.md](RECOVERY.md). Ordinary unknown retention, native SETTLE/RELEASE and equipment-key retention remain governed by their existing rules. Recovery clears only exact covered current blocks and never erases historical evidence or waives a budget ceiling.

Shared reservations require complete event history for reconciliation. Statistics accepted by the aggregate evaluator cannot replace it. Each budget history has its budget_digest, provider, source, as_of, status and a complete ordered journal. AVAILABLE requires complete:true and a natural revision equal to the number of journal entries. Other statuses retain explicit unavailability and cannot supply invented empty history. Each journal entry has a globally increasing sequence starting at 1 and an AGG event record. The latest entry for an event id determines its current ACTIVE or RETRACTED record. Earlier versions remain present. Exact repeated terminal reports can be new journal entries and do not add another contribution.

Every new supplied journal preserves the previously committed journal as an exact prefix. A shorter history, changed old row, skipped sequence, changed body at the same revision or mismatched provider/source/budget is an admission failure. Distinct conflicting complete snapshots at one revision cannot be resolved by sorting. Incomplete, unavailable, stale or contradictory observations withhold new reservations and retain existing exposure. The clock, as_of and freshness bound are explicit; no local time or hidden history lookup fills a missing fact.

The transition projects the latest complete event records into AGG's full EVENT_SNAPSHOT. It computes the query binding from the budget definition, current interval and proposed keys. It supplies all unsettled reservations for that budget independently of their age. This conversion does not add policy. The provider's assertion that the journal is complete, truthful and nonrollback remains a host premise.

A journal record that establishes a matched reserved effect substitutes committed exposure for that reservation exactly once. Its declared occurred_at determines committed window membership. Removing or retracting that record later does not silently release a reservation: the affected occurrence becomes DISPUTED, its unresolved reservation is retained, and affected new reservations are blocked until supported affirmative resolution. A revised terminal record with a different effect retains the earlier evidence and is treated as disputed exposure. A retraction of unrelated historical activity follows AGG semantics and remains visible in the journal.

## RES-005. Registration and reserve

REGISTER supplies one full definition, complete class authorizations and complete initial history. An administrative act binds the exact registry, event kind and full payload digest, identifies a HUMAN actor, principal, role, occurrence time and ACCEPT disposition, and has an attributed return through the registry's independently selected administration provider. The host supplies the complete selected authority basis for that actor and role, its current validity and revocation facts, and the exact authenticated act/return digests. Source confirmation or a machine credential cannot substitute for this organizational configuration act. Registration authorization is a distinct administration boundary, not an instance grant. Missing or negative acts cannot register a budget.

RESERVE supplies a complete current AUTHORITY input and full histories for every required budget anchor. The transition reevaluates AUTHORITY inside this same state transition. READY_FOR_RESERVATION is necessary but does not by itself authorize dispatch. Every reported required anchor must be registered, permit the stable class, have an exact class/envelope authorization, and project at least one selected contribution for this operation. All affected budget policies must name the same settlement provider and source and the same no-effect provider and source because one reservation and one lifecycle effect record reconcile the complete affected set. A request whose affected policies disagree on either pair is `UNSUPPORTED_RELATION`; it creates no reservation and changes no registry state. An authority result with empty `required_budgets` is valid when explicit per-action limits govern a `BOUNDED` operation or the operation declares `NONE`. The lifecycle creates a reservation input when exclusive keys apply, even without shared budgets; it creates none when both inventories are empty. A direct `aggregate-step` `RESERVE` with neither shared budgets nor exclusive keys is `UNSUPPORTED_RELATION`. An empty shared-budget set cannot satisfy a class whose policy requires a shared budget.

The transition evaluates committed contributions, distinct unsettled contributions and all new projected contributions against each affected partition. A proposal may affect several keys and budgets. All must be SATISFIED, and none may be blocked by unresolved effects. Missing history or authority produces a recorded WITHHELD decision, with the exact failed obligations retained and no new reservation. A violated bound also produces WITHHELD, distinct from invalid event admission.

On success, create one OPEN reservation retaining every selected contribution and return RESERVED. Its reservation permit expiry is the earliest of any nonnull fixed authority-envelope validity end and now plus each affected budget's or selected exclusive-key slot's declared permit duration. The lifecycle combines that expiry with now plus the proposal-capable step's required finite `permit_seconds` and uses the earlier instant for the dispatch permit. A lifecycle proposal with neither shared budgets nor exclusive keys creates no reservation input; its dispatch permit expires at the earlier of now plus the step's required finite `permit_seconds` and any nonnull fixed authority-envelope validity end. A deadline may stop later progression but does not replace or extend the dispatch-permit duration. The host must commit this state before dispatch and condition native execution on the exact occurrence and permit. The reference transition has not caused an external effect.

For RESERVE and RENEW, if any required numerical history is unavailable, incomplete, conflicting or stale, record WITHHELD with empty budgets and do not evaluate aggregates for that event. Retain the applicable history reasons. Existing authority, clock and exclusive-key precedence and the rules for committing current usable histories remain unchanged.

After existing authority, clock and exclusive precedence, first apply the existing unusable-required-history rule. When all required numerical histories are usable, inspect relevant retained actual effects and recovery packets under REC-008. If any affected actual accounting remains unassessed, RESERVE or RENEW is WITHHELD with empty budgets and no ordinary aggregate evaluation. A projectable actual lacking its prescribed journal record adds HISTORY_UNCORROBORATED and RECOVERY_EVIDENCE_INCOMPLETE; an unprojectable actual adds RECOVERY_EVIDENCE_INCOMPLETE. Retain independently applicable exposure-dispute and protected-pending-evidence reasons. Current usable histories still commit under the existing rules. Later repaired histories can restore numerical assessability; they do not clear LEAVE_UNRESOLVED's independent operational block. This unassessed-actual exception precedes the otherwise required aggregate evaluation for a blocked new contribution.

## RES-006. Renewal and rollover

RENEW identifies an existing OPEN or UNKNOWN reservation and supplies a complete current authority input for its unchanged exact proposal and envelope, together with full histories. A changed operation, class revision, proposal field or envelope is not a renewal. Reevaluate every current authority check, revocation and budget limit. Remove only this reservation's old unsettled contribution from the provisional pending inventory, then evaluate its same contribution once as the renewed proposal. Other pending exposure remains charged.

On success atomically replace its current authority evidence, permit expiry and receipt, returning RENEWED. Keep reservation id, occurrence and contributions unchanged. On refusal retain the previous reservation and its charge; do not extend its permit. Renewal is not a second permission to perform an operation already dispatched. The host's native deduplication and conditional-dispatch contract must distinguish continuation from another invocation.

An unsettled reservation remains charged once in every later window until matching settlement or authorized affirmative release. A new day, month, year, instance or authorized class does not free that capacity. Renewal at rollover tests the current committed window plus all still-unsettled exposure. Settlement then changes membership to the actual event time, which can be in a prior window; that change records the actual effect rather than pretending it happened at settlement time.

## RES-007. Settlement, unexpected effects and uncertainty

SETTLE supplies an attributed native outcome record, exact reservation reference when known, complete effect body, native event id and declared occurrence time, and full affected histories. The native record binds provider/source, original requested occurrence and exact observed fields. The host authenticates that complete record; the consumer checks its bindings and declared types. A record of acknowledgement or a timeout is not a terminal effect.

A matching terminal effect has the same occurrence and exact authorized native fields and appears exactly once in the current complete journal under its native event id. The transition marks the reservation SETTLED and removes its unsettled contribution only as the matching committed contribution enters history. Exact repeated evidence or repeated reports of the same effect do not add committed exposure. A second distinct effect for one occurrence is unexpected exposure, even when its arguments repeat the request.

Well-formed unexpected terminal evidence is retained, including foreign occurrence, changed arguments, excess quantity, changed grouping key or duplicate effect. It produces EFFECT_DISPUTED and a retained effect record, not an invalid-input refusal that makes the effect disappear. The original reservation remains charged while its outcome is unresolved. Actual projectable exposure is also represented by the history. Both original and actual affected partitions are blocked for new reservations. If the effect cannot be projected to a known typed partition, block the entire affected budget anchor and retain the full uninterpreted supplied record. The report distinguishes observed committed exposure from reserved uncertainty; it does not describe the latter as a second observed effect.

An outcome UNKNOWN retains the reservation and records the native evidence. Late matching evidence may settle it after permit expiry, authority expiry, withdrawal or scheduling cessation. Such evidence establishes what happened; it does not grant permission for another action. A stale expected revision requires retry against current state, while the host durably retains the incoming raw evidence. No consumer may tell a host to discard an unexpected effect because it did not conform to the proposal.

## RES-007A. Attributed historical exclusive-key coverage

[EXCLUSIVE-KEY-HISTORY.md](EXCLUSIVE-KEY-HISTORY.md) normatively defines complete per-slot guarantees, historical projection, independently authenticated source-request provenance, historical owner carriers, SEED_EXCLUSIVE, protected coverage and collision decisions, immutable retained snapshots and restart reconstruction. A mediated slot needs its own complete installed snapshot before reserve or renewal. All requested keys acquire atomically; uncertain or failed completion retains their occupancy. A provider tuple guarantee cannot establish another identifier’s freshness.

## RES-008. Affirmative release

RELEASE requires complete affirmative no-effect evidence from the declared no-effect provider/source, bound to the exact occurrence, reservation and original native request, plus a separate ACCEPT organizational release act with its selected authority basis and attributed return. The native record must have `completion_mismatch:false` and `mismatch_reason:null`. A changed or otherwise disqualified dispatch attribution uses `completion_mismatch:true` with `mismatch_reason:NATIVE_REQUEST_MISMATCH`; another unexpected or conflicting no-effect attribution uses `completion_mismatch:true` with `mismatch_reason:UNEXPECTED_EFFECT`. The transition retains either as disputed exposure and cannot release capacity. Qualifying no-effect evidence must expressly rule out a past effect and future effect from the outstanding invocation. A timeout, request to cancel, revoked grant, permit expiry, empty current window or an agent's unsupported assertion supplies neither fact.

An actual release is supported only for an OPEN or UNKNOWN reservation with no conflicting terminal effect. A disputed or already settled occurrence cannot change to RELEASED through this profile. A `RELEASE` event against terminal state remains admissible only to retain a same-fact duplicate or contradictory `NO_EFFECT` record under the exact prior-state table in `RESERVATION-RECORDS.md`; it does not release a settled or disputed occurrence. Removing a pending charge produces RELEASED, retains all evidence and advances one revision. A later attributable effect contrary to the no-effect record is retained as a dispute and blocks the affected budget; release never permits erasing evidence. General cancellation, compensation and automated resolution of contradictory native records remain unsupported.

## RES-009. Reference host and qualification

The in-memory reference host owns one selected current state and serializes aggregate-step calls through a single queue or lock. It admits two independent clients, commits a returned next state only after successful transition, and exposes restart by complete exported state. Its contention test begins with committed exposure 800 and cap 1000. Each client proposes 150. Both proposals are independently within the bound against revision n. Exactly one can reserve at revision n. The other's stale revision is rejected unchanged. After reading revision n+1 and submitting a new event, its aggregate is 1100 and the reservation is withheld. The ledger retains only one 150 pending charge.

Qualify that single-process behavior separately from pure transitions. Process memory does not establish durable recovery, distributed coordination, authenticated observations or atomic native dispatch. The host must preserve incoming unknown-effect evidence across crashes and enforce the exact committed permit at every covered native mutation path. Passing the arithmetic evaluator does not supply those obligations.

Decisive cases must cover shared instances and classes; stale/altered/exact retries; state interchange and restart; atomic multiple partitions; history revisions/retractions; all reducer boundaries; unavailable/stale/conflicting history; rollover and renewal; matched/late/unknown/unexpected effects; prohibited automatic release; authorized affirmative release; and changed-definition attempts. Every semantically valid mutation that drops pending exposure, counts a proposal twice, bypasses an authority check, releases on timeout, discards an unexpected effect or changes one partition before another fails must be detected. Schemas and exact state outputs remain required before claiming this profile qualified.
