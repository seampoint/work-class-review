# Current permission holdings

Status: `DRAFT_NOT_ADOPTED`, `APPARATUS_ONLY`. This profile defines a bounded authoritative permission registry, its independently authorized changes and current reliance by work classes. Permission possession satisfies only an expressly selected permission condition. It grants no business authority, approval, disclosure authority or exception.

## HOLD-001. Registry and conflict policy

One immutable configuration identifies the registry, principal, policy revision, permission catalogue, incompatible pairs, administration role, provider, source, protected channel, clock source, actor namespace, identity provider and identity revision. Its digest is `digest("holdings-configuration", configuration)`. Its specification pin equals the selected candidate. Permission identifiers are sorted unique UTF-8 identifiers. Each conflict has `left < right` in UTF-8 order; the pairs are sorted unique by their complete canonical bytes. Both members exist in the catalogue and differ. An unknown member, reversed pair, duplicate or self-pair is `DEFINITION_INVALID`.

A conflict prohibits the same canonical actor from holding both permissions at the same instant in this principal and registry. It spans all participating work classes and instances. The configuration cannot change under an established registry. Policy migration, prerequisite relations, approved exceptions, future scheduled grants and automatic cascades are unsupported. A host must select the same authoritative registry for every work class governed by the policy. Selecting another class, case, alias or approver cannot reset holdings.

The host authenticates configuration selection and resolves each person or machine to the stable actor namespace and identity revision declared in the configuration. The consumer compares exact identifiers; it cannot determine that two unequal account names denote one person. An identity namespace change, alias merge or split requires explicit host treatment and cannot silently create a new permission inventory. Hashing a configuration or actor identifier does not authenticate it.

## HOLD-002. Initialization and human administration

`holdings-step` receives the closed `holdings.schema.json` input: schema, candidate pin, configuration, nullable complete prior state and digest, event and host evidence. A null state is admitted only with a null state digest. The first event is `INITIALIZE`, with expected revision `"0"`, null expected state digest and the complete existing grant inventory. Initialization requires an available snapshot clock, the exact accepted human administration act and authenticated return, and a protected completeness attestation whose inventory digest is `digest("holdings-seed-inventory", event.payload.grants)`. Missing completeness evidence is `EVIDENCE_UNAVAILABLE`; a mismatched inventory digest is `DEPENDENCY_MISMATCH`. The host establishes that the selected inventory is complete. No model or caller-supplied list establishes completeness itself.

Initial grants are sorted unique by grant identifier. Each has an actor, catalogue permission, inclusive `valid_from` and nullable exclusive `valid_until`. Every imported grant is active at the snapshot instant. Duplicate active actor/permission pairs and imported incompatible holdings are `STATE_INVALID`. Initialization cannot import a violation for later repair. An accepted initialization creates revision `"1"`. Another fresh initialization against established state is `DEFINITION_CONFLICT`.

Every fresh event requires a current host-selected HUMAN administration basis for this configuration, principal, administration role, exact actor and event kind. The basis names provider, source, observed instant, inclusive validity start, nullable exclusive end, nullable revocation instant and evidence reference. The observed instant equals the event clock. Its allowed operations are a sorted unique subset of `GRANT`, `INITIALIZE`, `REVOKE`. A permission holder or model assessment cannot supply this designation.

The administration subject is `digest("holdings-administration-subject", {configuration_digest,event})`, with only `event.administration` omitted from that event projection. The accepted act binds its basis identifier, actor, principal, role, event kind, complete subject and event instant. The return retains the complete canonical act bytes, `digest("holdings-administration-act", act)`, actor, provider, source, protected channel, return instant, evidence reference and provenance digest. Return instant equals the event clock. Host evidence authenticates exactly the selected `ADMIN_BASIS` and `ADMIN_RETURN` digests, using `holdings-administration-basis` and `holdings-administration-return`; their provider and source match configuration, and the return channel matches the protected channel. A basis authentication record has null channel. Records are sorted unique by complete canonical bytes. Real authentication and custody are host responsibilities.

Within administration checks, validate exact basis/act/return bindings, canonical return bytes and host authentication before current validity and accepted status. Missing administration is `ADMINISTRATION_NOT_ESTABLISHED`. Missing return or required authentication is `EVIDENCE_UNAVAILABLE`. Mismatched subject, identity, provider, source, channel or returned body is `DEPENDENCY_MISMATCH`. Embedded byte decoding and canonical failures use `ARTIFACT_ENCODING_INVALID` or `ARTIFACT_NONCANONICAL`. A wrong remit, noncurrent designation, revoked basis or rejected act is `ADMINISTRATION_NOT_ESTABLISHED`. Invalid calendar instants are `CLOCK_INVALID`. Historical administration is checked at its retained event instant, without requiring that administrator to remain designated today.

## HOLD-003. Complete state and reconstruction

State contains schema, specification pin, core and revision-ordered records. Core contains the configuration digest, revision, last available clock instant and retained grants sorted unique by identifier. Each retained grant adds nullable `revoked_at` to its original immutable grant fields. Expired and revoked grants remain in the inventory. Each record retains the complete event and host evidence, event digest, complete receipt and receipt digest. The event digest is `digest("holdings-event", {event,host_evidence})`.

A receipt contains schema, event identifier and digest, nullable prior state digest, new revision, next core digest, decision, ordered reasons and protected channel. Core and receipt digest kinds are `holdings-core` and `holdings-receipt`. The receipt identifies the next core, excluding records, so it does not incorporate the digest of the state containing itself. The complete returned state digest is `digest("holdings-state", state)`.

State admission reconstructs initialization and every retained transition in order against the supplied immutable configuration. It compares complete reconstructed core, events, receipts, revisions and digests. A correct outer hash alone is insufficient. Missing, reordered, duplicated, altered or impossible history is `STATE_INVALID`. A supplied state digest mismatch is `DIGEST_MISMATCH`; configuration dependency mismatch is `DEPENDENCY_MISMATCH`. State and configuration pins must select this candidate. Historical host evidence is retained historical input, not current authority. Protected latest-state selection and prevention of rollback remain host obligations.

## HOLD-004. Grant and revocation decisions

`GRANT` carries a fresh grant identifier, target actor, permission and nullable exclusive validity end. The grant begins at the available event clock. The permission must exist in the configured catalogue. A retained grant identifier cannot be reused, including after expiry or revocation. Unknown permission or reused identifier is `DEPENDENCY_MISMATCH`; a finite end at or before the event instant is `CLOCK_INVALID`.

First check whether that actor already holds the exact permission at the event instant. If so, record `UNCHANGED` with reason `ALREADY_HELD`. This creates no second grant, does not replace the first grant identifier and cannot extend its end. Otherwise compare the requested permission with every active holding of that actor. An incompatible pair records `WITHHELD` with `CONFLICTING_HOLDING` and changes no grants. An allowed request records `GRANTED` and retains the new grant with null revocation instant. Conflict checks and admission of the resulting inventory are one expected-revision transition. Two individually valid requests cannot jointly establish an excluded pair.

`REVOKE` names the exact retained grant identifier, actor and permission. An unknown or mismatched target is `DEPENDENCY_MISMATCH`. An already revoked or naturally expired target records `UNCHANGED` with `NOT_ACTIVE`. An active target records `REVOKED` and sets its revocation instant to the event clock. An old revoke cannot remove a later grant with another identifier. Revocation of permission is distinct from withdrawing a human approval. A later authorized regrant may satisfy a current permission condition again; permanent invalidation of an approval requires a separate explicit approval policy.

Active membership requires `valid_from <= at`, `at < valid_until` when finite, and `at < revoked_at` when revoked. Time alone can end membership without a registry event. Historical results are not current permission evidence. Every admitted decision, including `UNCHANGED` and `WITHHELD`, retains its complete attempted event and advances revision. Admission refusals change nothing.

## HOLD-005. Order, replay and finite limits

Apply checks in this order: closed shape and canonical input size; candidate/configuration and complete state admission; exact event replay; fresh expected revision and state digest; available ordered event clock; exact human administration; retained-event capacity; target and policy checks; projected grant capacity. After shape admission a refusal echoes exactly the supplied nullable state and state digest. Malformed outer shape uses the protocol's generic refusal. Event expected revision or digest mismatch is `REVISION_CONFLICT`. Clock source mismatch, unavailable clock, invalid calendar instant or backward clock is `CLOCK_INVALID`. Equal serialized instants are permitted.

An event identifier is unique within this registry. Exact replay compares its complete event and host evidence before fresh revision, clock or administration checks. It returns the original receipt and receipt digest with the current complete state and `replay:true`, changing no revision and granting no new permission. Changed bytes under that identifier are `REPLAY_CONFLICT`. Read access to replay responses still requires independent current host authorization; historical administration does not authorize a present reader.

The profile supports at most 64 permission identifiers, 128 incompatible pairs, 256 retained grants, 64 retained events including initialization, 32 requirements per authority envelope and eight registry bases per authority input. Canonical holdings-step input is at most 16,777,216 bytes. Closed-shape collection overflow is `SCHEMA_INVALID`; supported-shape byte overflow and projected retained-inventory overflow are `LIMIT_EXCEEDED`. Existing authority outer and independent-evidence byte limits remain in force; the standalone holdings limit does not enlarge them.

At 256 retained grants, an admitted no-op or conflict still records if event room exists, because it adds no grant. A genuine new grant refuses unchanged. At 64 retained events, exact replay, export and historical reconstruction remain available, but fresh mutations refuse `LIMIT_EXCEEDED`. Fresh business authority and commitment from that exhausted registry withhold `HOLDINGS_CAPACITY_EXHAUSTED`, even when a permission is still present. The registry cannot continue authorizing work while unable to retain revocations. No pruning, silent reset or automatic rollover is defined; the host requires protected intervention and a separately selected continuation policy. This finite reference profile makes no unlimited-history claim.

## HOLD-006. Current holdings in authority

An optional sorted unique envelope `holdings_requirements` inventory names each requirement's id, step, exact configuration digest, permission and actor selector `EXECUTOR` or `GATE_ACTOR`. The selected step exists. `GATE_ACTOR` resolves the unique admitted ordinary `INSTANCE_DECISION` for `DECIDE` or `VERIFY` for `VERIFY`, constrained by gate role and selected act digest. For independent decisions, it resolves only the decision explicitly named by `gate.decision_requirement`. `NONE` supplies no gate actor; a `GATE_ACTOR` requirement on that step refuses `UNSUPPORTED_RELATION` during static admission. Unsorted or duplicate requirement identifiers refuse `INPUT_INVALID`, and an unknown selected step refuses `REFERENCE_INVALID`. Another successful decision, grantor, attester, arbitrary act or caller-provided actor cannot substitute. Independent evidence leaves do not declare nested holdings requirements in this profile.

For the selected step, each distinct required configuration has exactly one supplied complete holdings basis. A basis carries configuration, reachable complete state, exact state digest and protected host selection. The selection binds configuration digest, state digest, revision, provider, source, channel, exact authority query instant, selection evidence and `AVAILABLE`, `UNAVAILABLE` or `CONFLICTING` status. Configuration principal equals the authority envelope principal, and its clock source equals the authority clock source. Phase 2 admits supplied configuration and state, retaining `DEFINITION_INVALID`, `STATE_INVALID`, `DIGEST_MISMATCH` or `CLOCK_INVALID` where applicable. Historical reconstruction failures, including invalid retained administration, become `STATE_INVALID`. An invalid calendar value in the current selection instant is `CLOCK_INVALID`; a valid instant unequal to the query instant is evaluated as stale in phase 5. The phase-2 code order in AUTHORITY-CHECKS.md applies across all independently checkable supplied bases, rather than their array order. Phase 3 checks extra or duplicate bases as `BINDING_MISMATCH`; mismatched configuration, principal, permission, provider or source is `DEPENDENCY_MISMATCH`. These bindings are checked before current membership decisions. Lifecycle and dispatch wrappers preserve these admission refusals rather than recording them as policy withholding.

Phase 5 adds `HOLDINGS` checks for exact selected actor, permission, configuration and instant. The check subject is `digest("holdings-query", {requirement,actor,at})`; its reference is the requirement id and its time is the authority clock. Missing basis or unavailable/conflicting selection withholds `HOLDINGS_UNAVAILABLE`. An available selection at another instant, or a query before retained `last_clock`, withholds `HOLDINGS_STALE`. A capacity-exhausted registry withholds `HOLDINGS_CAPACITY_EXHAUSTED`. Otherwise missing, expired or revoked membership withholds `CURRENT_HOLDING_REQUIRED`. Successful membership records the corresponding exact successful check. These reasons participate in ordinary deterministic reason ordering and `AUTHORITY_NOT_ESTABLISHED`. An unavailable authority clock follows the existing clock refusal before querying holdings.

Complete authority evidence digests retain `holdings_bases` when supplied, including an explicit empty array. Absence and an explicit empty array are distinct evidence bytes but have the same policy meaning when no holding is required. Historical human signing validity remains separate from the enclosing operation's current permission condition. A current reviewer condition does not require a live reviewer session or erase a past signed act. The host authenticates the selection and establishes that this is the latest authoritative state; a self-consistent old state cannot prove freshness.

## HOLD-007. Dispatch and commitment evidence

A lifecycle step with nonempty holdings requirements uses `SOURCE_REQUIREMENTS` for fresh dispatch authorization in this profile. A missing dispatch gate or another gate kind refuses `UNSUPPORTED_RELATION` before policy evaluation or permit creation. Direct authority evaluation does not require a lifecycle dispatch gate. Its source requirements and holdings requirements together contain at most 64 members; exceeding that combined projection bound is `LIMIT_EXCEEDED` both before `PROPOSE` can create a permit and at dispatch. The exact envelope inventory remains immutable between proposal and dispatch. Complete holdings bases are refreshed evidence, alongside clock and source observations. A fresh authority evaluation must pass at the dispatch instant. Missing, revoked, expired or unavailable current holdings record ordinary `WITHHELD`; they cannot reuse proposal eligibility.

The closed source-vector fence gains an exact `holdings` array when required, sorted unique by requirement id. Each row derives directly from the admitted current basis and selected actor: requirement id, configuration digest, state digest, revision, actor, permission, unique active grant id and nullable exclusive grant end. The dispatch authorization scope digest includes this complete array, in addition to its existing source vector and exact invocation identity. No scalar observation or caller-supplied Boolean substitutes for reconstructed membership. The retained `AUTHORIZATION` decision detail copies the same complete `holdings` array when it is present in the derived fence, and omits it when absent. Retained decision integrity reconstructs that exact projection. Missing, extra, duplicated or changed fence rows are `BINDING_MISMATCH`.

Authorization expiry is capped by every finite selected grant end, alongside existing permit, envelope, decision and source validity limits. An unbounded grant adds no finite cap. At commitment the host rechecks exact selected state revisions and digests, current membership and authorization expiry in the same ordering as every participating grant/revoke writer. Any intervening registry decision, even unrelated to the selected permission, requires a fresh authorization. Time-based expiry blocks commitment even when the state digest is unchanged. Every reusable query or cache key includes its query instant; a state digest alone cannot identify current membership.

## HOLD-008. Host ordering and protected records

Before invoking the exact native request, the host atomically retains its unique invocation identity, current authorization, selected holdings revisions and intent under the same coordinator that orders participating permission writers. The commitment point is the selected provider's conditional acceptance of that exact native operation while its covered current conditions hold. Recording an intent is not proof of native effect. A pre-dispatch read or lock released before conditional commitment is insufficient. Where a provider offers no conditional boundary, one mediator must cover all relevant administrative and native paths. The contract cannot make an unmediated path participate.

The process-local reference exercise holds one lock across current checks, intent retention and synchronous stub commitment. It demonstrates only those serialized paths. Before intent retention, a failed write returns `COMMIT_FAILED` with unchanged authoritative state and no invocation. After retained intent and before invocation, a stopped or failed attempt remains pending for reconciliation. After possible connector acceptance, any exception, crash or failed outcome write leaves the retained intent uncertain and prohibits blind reinvocation. Restart or exact retry returns the retained pending/uncertain invocation record and requires protected reconciliation; it does not infer no effect. An established result is retained against the exact invocation identity. No provider deduplication, lookup, cancellation or financial filing capability is presumed.

Hosts separately authorize readers of detailed permission states, receipts, replay responses, conflicts and audit exports. Detailed adapter results are protected internal records; they are not customer-facing responses. Public failure responses contain no actor, permission, report, conflicting owner, receipt or denial details. The organization selects reader policy, retention, deletion, encryption and audit custody. This profile declares the protected channel and exact bindings; it does not implement full information-flow mediation or a universal retention policy. Process-local results do not establish durable recovery, distributed coordination, actual all-writer coverage or complete industry workflow integration.
