# Adapter protocol and conformance

Protocol identity: `seampoint.work-class.adapter/1.0.0-draft.2`. Status: `DRAFT_NOT_ADOPTED`, `APPARATUS_ONLY`. This protocol retains the eight operation names and defines their draft-2 inputs and results. It does not require a network service or impose internal component boundaries.

## WCS2-010. Transport and schema resolution

A program reads one restricted UTF-8 JSON object per line from standard input and returns one canonical JSON object followed by one LF byte on standard output. A request has exactly `protocol`, `request_id`, `operation`, and object-valued `input`. A normal response has exactly the same `protocol`, `request_id` and operation plus a closed `result`. `protocol.schema.json` has a top-level union of those closed request and response envelopes. Every protocol-error response uses the adapter's supported protocol identity, including when the input named another value. If a parsed object has a recognized operation but the protocol or envelope is invalid, the response uses that recognized operation and result `{"status":"REFUSED","code":"PROTOCOL_INVALID","path":""}`. If the operation is an unrecognized but valid identifier, the protocol-error response echoes it. A missing or malformed operation becomes null. A valid request identifier is echoed; a missing or malformed identifier becomes null. Invalid UTF-8, duplicate keys, JSON numbers, invalid Unicode and an unterminated final line are transport errors. The program terminates nonzero without a governance result for that line. Diagnostics use standard error. Processing one request cannot depend on a fixture identifier, corpus file or process-local request history.

The recognized operations are `capabilities`, `validate`, `evaluate`, `aggregate-step`, `deploy`, `step`, `readback`, and `check-evidence`. A consumer claims the operations and roles it implements in `capabilities`. A profile or role outside that claim returns `ROLE_UNSUPPORTED`. A missing or unknown required kind returns `SCHEMA_INVALID`. The consumer cannot fall back to another protocol.

The candidate supplies a closed schema graph. `schema-bundle.json` maps each exact schema URI to one candidate-relative file. A consumer resolves a listed URI only through that mapping. An unlisted URI is unresolved and returns `REFERENCE_INVALID` for an otherwise admitted artifact reference. A source reference, artifact identifier or schema reference cannot trigger network or undeclared filesystem access. `aggregate.schema.json`, `authority.schema.json`, `reservation.schema.json`, `work-class.schema.json`, `lifecycle.schema.json`, `evidence.schema.json`, `boundary.schema.json`, and `protocol.schema.json` are the complete public graph.

Every public object boundary is closed. Each schema object either declares its complete properties and rejects additional properties, or selects a finite set of closed variants. A schema-control failure blocks candidate freeze when any public object relies on an unconstrained `type: object`.

## WCS2-011. Capabilities and roles

`capabilities` input is exactly `{}`. Its result has exactly `status`, `protocol`, `specification_pin`, `roles`, `operations`, `tzdb`, and `limits`. `status` is `CAPABILITIES`; `protocol` identifies this adapter; and the pin is the SHA-256 digest of the exact draft-2 contract manifest bytes. Roles and operations are sorted, unique UTF-8 identifier lists. `tzdb` is `2025a` when calendar aggregate evaluation is supported and null otherwise. A capabilities result is a claim to test, not a certificate.

Runtime roles are `LINEAR_WORK_RUNTIME`, `CHOICE_LOOP_RUNTIME`, `DEADLINE_RUNTIME`, and `PARALLEL_FANOUT_RUNTIME`. Their profiles are cumulative in the order defined by `LIFECYCLE.md`. The exact pairs are `LINEAR` with `LINEAR_WORK_RUNTIME`, `CHOICE_LOOPS` with `CHOICE_LOOP_RUNTIME`, `DEADLINES` with `DEADLINE_RUNTIME`, and `PARALLEL_FANOUT` with `PARALLEL_FANOUT_RUNTIME`. Any other admitted-enum pair is `ROLE_UNSUPPORTED` before definition or state checks. The remaining roles are `AGGREGATE_EVALUATOR`, `AUTHORITY_EVALUATOR`, `SHARED_BUDGET_TRANSITIONS`, `REFERENCE_SINGLE_PROCESS_CONTENTION`, and `REVIEW_EVIDENCE`. A claimed runtime role includes the authority and shared-budget consequences of every admitted operation. An implementation cannot claim that its caller performed those parts outside the tested lifecycle.

A pure transition consumer cannot claim `REFERENCE_SINGLE_PROCESS_CONTENTION`. That role requires separate tests of serialized access to one work state and every affected shared budget, atomic commit, two-client contention, and export for restart. It does not imply durable storage or distributed coordination.

## WCS2-012. Operation contracts

`protocol.schema.json` selects the exact closed input and result schema for each operation. Duplicate keys and malformed JSON are transport failures before artifact admission. Within a decoded artifact, a duplicate key returns `ARTIFACT_ENCODING_INVALID`; a forbidden JSON-number token or a canonical-byte mismatch returns `ARTIFACT_NONCANONICAL`. Other structural errors in an operation input return `SCHEMA_INVALID`. Once a request's state is structurally admitted, a stateful refusal returns that exact supplied state and every supplied budget state unchanged. A malformed outer request has no admitted state to echo.

### `validate` and `readback`

Both inputs have exactly `kind`, `specification_pin`, and `artifact_bytes_base64`. The recognized artifact kinds are `AGGREGATE_DEFINITION`, `AUTHORITY_DEFINITION`, `WORK_CLASS`, `BOUNDARY_RECORD`, and `EVIDENCE_RECORD`. Base64 carries the original artifact bytes through the adapter envelope. The consumer decodes the bytes, enforces the restricted canonical JSON rules, checks the selected candidate and schema identity, resolves references only through the schema bundle and then applies the subsystem's static checks. Successful artifact digests use `aggregate-definition`, the authority definition's declared domain, `work-class-definition`, `boundary`, or `evidence` respectively.

Validation success is exactly `{"status":"ACCEPTED","digest":<artifact digest>}`. Readback success contains exactly `status`, `digest`, and `lines`; `status` is `READBACK`. Each line contains exactly a JSON Pointer `path` and canonical scalar or empty-collection `value` string. Readback covers every operative field. It does not interpret source prose or prove fidelity to an English policy.

### `evaluate`

The input has exactly `kind` and `request`. `AGGREGATE` selects the complete aggregate input and result. `AUTHORITY` selects the complete authority input and result. Both receive explicit clock and evidence facts. An authority result of `READY_FOR_RESERVATION` identifies an exact current proposal that has passed the authority checks. It is not a permit and cannot authorize dispatch.

### `aggregate-step`

The input is the complete reservation transition input in `reservation.schema.json`, without another kind wrapper. `REGISTER`, `RESERVE`, `RENEW`, `SETTLE`, and `RELEASE` are reservation event kinds rather than adapter operations. A transition result includes the complete receipt, receipt digest, next reservation state, state digest, and replay flag. A stateful refusal echoes the exact prior reservation state. The independent interface and the composite lifecycle use the same reservation semantics.

### `deploy`

The input is the closed `deployInput` in `lifecycle.schema.json`. It contains exactly the selected profile and corresponding role, candidate pin, complete work-class definition and digest. The selected profile equals `definition.profile`; an admitted profile-role pair with another definition profile is `BINDING_MISMATCH`. It also contains instance identity, complete deployment authorization, the complete organizational-authorization, correspondence, source-confirmation and policy-decision evidence records named by it, an available authorization clock and the exact `initial_clocks` array required by root deadlines. The authorization binds the exact candidate pin, work-class digest, profile, role and instance, along with the organization and the four evidence digests. LIFE-003 defines the checks on the three review records. The organizational evidence binds the `deployment-authorization-subject` digest of the record before its evidence-digest field is populated; the complete record receives a separate `deployment-authorization` digest. The implementation verifies both digests and the evidence status, subject, organization and validity at the authorization-clock instant. A null deployment-authorization expiry has no fixed upper bound; a nonnull expiry is exclusive and must be later than that clock. A bare accepted status and ambient time are not sufficient. `initial_clocks` follows LIFE-003 and is empty when no root deadline requires it.

Success is the closed `deployResult`. It identifies the profile, role, instance, work-class digest and complete deployment-authorization digest and returns the complete initial work state and digest. That state retains the deployment-authorization record, the four evidence records, their exact subject, record and evidence digests, and the authorization clock so a restart can recompute every binding and time relation. It activates the root occurrence. It creates no operation permit, shared reservation, dispatch or effect record. A malformed request that prevents profile and role admission returns the generic shape refusal. Once those values are admitted, a deployment failure returns the closed lifecycle refusal `{status,profile,role,code,path}` with the exact admitted profile and role and no state.

### `step`

The input is the closed `stepInput` in `lifecycle.schema.json`. It contains exactly the selected profile and role, candidate pin, complete work-class definition and digest, complete prior state and digest, and one closed lifecycle event. The selected profile equals `definition.profile`; the state profile and role equal the request pair; and the state work-class digest equals the supplied definition digest. An otherwise admitted mismatch is `BINDING_MISMATCH`. The event is exactly one of `PROPOSE`, `DISPATCH_OBSERVED`, `EFFECT_OBSERVED`, or `CLOCK`.

`PROPOSE` contains one exact occurrence, native request, executor, credential set, complete authority input, zero or one required registry-scoped budget input with expected revision, accepted clock revision and observation digests. It represents either the first proposal for an active occurrence or the renewal of an expired, undispatched permit under LIFE-007. A nonempty input names one reservation registry and the sorted anchor set changed by its one complete reservation transition. The consumer first checks declared bindings to unique completed ancestor effects, evaluates current authority, checks declared cross-occurrence actor separation and then applies the reservation rules. Success returns one permit containing the exact retained bases and changes the work state and the one affected reservation-registry state together. An authority or separation withholding records `WITHHELD` and leaves the registry unchanged. A reservation policy withholding records both the work decision and the registry's withholding receipt and next revision. A malformed, stale or wrongly bound proposal is an admission refusal and leaves every supplied state unchanged.

`DISPATCH_OBSERVED` contains the complete committed permit, exact native request, connector identity, attempt, acknowledgement and the exact latest retained available clock revision used to validate the attempt timeline. The attempt time cannot precede the permit clock or follow the selected dispatch clock, and permit expiry is tested against that attempt time. A changed native request with `NOT_SENT` and no accepted acknowledgement produces `DISPATCH_REFUSED`; any mismatch that may have reached the connector produces `DISPUTED` and an unknown occurrence state. A matching attempt is retained. Its acknowledgement does not settle exposure or advance the work graph.

`EFFECT_OBSERVED` has a governed branch and a foreign branch. The governed branch contains the complete permit, dispatch digest, provider-native operation identity, native evidence, actual scalar fields, typed collection fields, effect status, event time, observation time, nullable completion authorization, zero or one registry input, and the activation-clock copies required by newly activated deadlines. The foreign branch supplies null permit, dispatch and completion authorization plus the provider-native operation identity. An authority-only foreign effect supplies an empty affected-anchor set and no registry input. A budget-bearing foreign effect supplies a nonempty exact affected-anchor set and one matching registry input. An exact governed effect can settle reservations and advance the graph. The effect, dispatch-attempt, observation and selected registry-clock times must satisfy LIFE-010; a well-formed established effect with a contradictory claimed timeline is retained and disputed rather than allowed to route or free capacity. Unknown, foreign, unexpected, conflicting and late effects are retained according to `LIFECYCLE.md` and `RESERVATION-RECORDS.md`. No effect can complete an occurrence without a committed permit and exact dispatch binding.

`CLOCK` contains one exact available, unavailable or conflicting clock record and the activation-clock copies required by any successor deadlines created by expiry routing. Only an available admitted clock revision advances runtime time and evaluates deadline predicates. Proposal, dispatch and effect timestamps do not advance the lifecycle clock.

Success is the closed `stepResult`. It contains exactly `status`, `profile`, `role`, `decision`, `decision_digest`, `permit`, `budget_results`, `state`, `state_digest`, `transition_state_digest`, `transaction_digest`, and `replay`. Each affected budget result contains its reservation-registry digest, affected anchor set and complete reservation transition result. `transition_state_digest` is the original decision's `state_after_core_digest`; `state_digest` identifies the complete returned state through the projection in LIFE-019. They are different identities. On exact replay, the decision, permit, budget results, transition-state digest and transaction digest are the original transition values, while `state` and `state_digest` are current. The transaction digest binds the prior work state, event, decision, original next-state core and every original budget result without creating a circular digest. The host commits the complete transition before dispatch.

An exact replay returns the retained historical transition fields and the current complete state with `replay:true` and creates no new state revision. Reuse of an event identifier with changed canonical bytes returns `REPLAY_CONFLICT`. A new event submitted against a stale state or budget revision returns the corresponding revision refusal.

The reference host reports authoritative initial-root installation through the closed `hostDeploymentResult` and commit-before-dispatch through the closed `hostCommitResult` in `lifecycle.schema.json`. These host results are exercised by the reference-host harness and are not adapter operations. An exact duplicate installation returns the established state as an idempotent replay; a conflicting installation returns `INSTANCE_OCCUPIED`. `COMMIT_FAILED` returns the unchanged authoritative work and budget digests and `dispatch_performed:false`.

### `check-evidence`

The input is one of two closed evidence inputs in `evidence.schema.json`. The basic form contains the profile, `REVIEW_EVIDENCE` role, candidate pin, exact subject and a source-confirmation, policy-decision, organizational-authorization or review record. `subject.subject_digest` is the externally computed digest of the exact artifact or record named by `subject.kind` and `subject_id`; it is not a digest of the subject wrapper. The evidence record's subject digest must equal it. The consumer checks candidate, pin, exact equality and accepted status. Variant-specific scope arrays are closed, sorted record content, but this basic input supplies no expected scope universe and therefore does not establish scope sufficiency.

The correspondence form also supplies the complete work-class definition and digest plus one correspondence record. The subject kind is `WORK_CLASS`; its ID equals the definition ID; and `correspondence.subject_digest`, `subject.subject_digest`, `correspondence.work_class_digest`, and `work_class_digest` all equal `digest("work-class-definition",work_class)`. The input pin and subject pin both equal `work_class.specification_pin`, and the input profile equals `work_class.profile`. The record source ID and revision equal the definition's source. The consumer derives the complete source-obligation inventory and the complete readback provision-path universe, verifies the exact source-obligation partition, the complete provision-path coverage with no mapped/unsupported overlap, edge uniqueness, and one residue row per uncovered member, and verifies the nested accepted review against `digest("correspondence-subject",correspondence_without_review)`. A digest, identity, pin, partition, residue, or review-subject mismatch is `BINDING_MISMATCH`. A structurally missing review is `SCHEMA_INVALID`; a present review whose status is not `ACCEPTED` is `EVIDENCE_NOT_ACCEPTED`. This establishes mechanical coverage accounting and exact review binding, not semantic fidelity.

A successful result contains exactly `status`, `profile`, `role`, `subject_digest`, `evidence_digest`, and `specification_pin`. `evidence_digest` is `digest("evidence",evidence)`. A failed check whose profile and role were admitted returns those identities in the closed `EVIDENCE_INVALID` result with `BINDING_MISMATCH`, `EVIDENCE_NOT_ACCEPTED`, `EVIDENCE_UNAVAILABLE` or `SCHEMA_INVALID`. A malformed input uses the generic shape refusal. The operation establishes only the mechanical facts stated for its basic or correspondence form. It does not authenticate the actor, prove observation truth, establish the semantic adequacy of a scope or mapping, or qualify a production deployment. Deployment separately checks the full deployment-authorization record, its organizational-authorization evidence and its correspondence, source-confirmation and policy-decision evidence under LIFE-003.

## WCS2-013. Evaluation order and result classes

The adapter applies checks in this order: transport and envelope; protocol, operation, candidate, role and profile selection; closed schema; canonical bytes and declared artifact identity where applicable; definition and state digest; exact replay; instance, occurrence, proposal, permit, dispatch, evidence and clock binding; event prerequisites; the retained proposal-count ceiling for `PROPOSE`; current authority, including its required clock and observations; the initial-proposal actuation ceiling; shared-budget revision and policy; effect-carrier classification and declared route selection; effect- or clock-driven structural composition preflight. A higher-precedence failure determines the result. Permit renewal does not use the actuation ceiling.

An admission refusal has `status:REFUSED`, a typed code and `path:""` in this candidate. The empty path avoids implementation-dependent diagnostic pointers; implementations may report diagnostics outside the canonical conformance result. A refusal creates no governed decision. Where the runtime state has been admitted, the lifecycle refusal also carries the selected profile and role and the exact supplied work and budget states. An admitted policy decision records the event identity and digest in the state checkpoint, requires the host to retain the complete canonical request and response preimages under LIFE-019, and advances the work-state revision even when its disposition is negative or stopping. `WITHHELD`, `DISPATCH_REFUSED`, `OUTCOME_RETAINED`, `FAILED`, `EXPIRED`, `STOPPED`, and `DISPUTED` are admitted decisions rather than input refusals.

The common and lifecycle admission-refusal vocabulary is `ADMINISTRATION_NOT_ESTABLISHED`, `ARTIFACT_ENCODING_INVALID`, `ARTIFACT_NONCANONICAL`, `BINDING_MISMATCH`, `CLOCK_INVALID`, `DEFINITION_CONFLICT`, `DEFINITION_INVALID`, `DEPENDENCY_MISMATCH`, `DIGEST_MISMATCH`, `EVIDENCE_UNAVAILABLE`, `INPUT_INVALID`, `INSTANCE_NOT_ACTIVE`, `LIMIT_EXCEEDED`, `OCCURRENCE_CONFLICT`, `OCCURRENCE_NOT_ACTIVE`, `PREREQUISITE_MISSING`, `PROTOCOL_INVALID`, `REFERENCE_INVALID`, `REPLAY_CONFLICT`, `RESERVATION_NOT_FOUND`, `REVISION_CONFLICT`, `ROLE_UNSUPPORTED`, `SCHEMA_INVALID`, `STATE_INVALID`, `TYPE_INVALID`, `UNSUPPORTED_FEATURE`, `UNSUPPORTED_RELATION` and `VERSION_UNSUPPORTED`. Embedded authority and reservation admission failures retain the same code from this union. Direct authority evaluation also has the closed policy-refusal codes `ACT_CONFLICT`, `GATE_REQUIRED`, `ACT_NOT_AUTHORIZED`, `ACT_NOT_ACCEPTED`, and `AUTHORITY_NOT_ESTABLISHED` defined by `AUTHORITY-CHECKS.md` and `authority.schema.json`; the lifecycle maps those results to admitted `WITHHELD` decisions rather than admission refusals. Decision reason codes are a separate vocabulary defined by the applicable lifecycle or subsystem rule.

Expected results are derived from the normative rule and exact input before either implementation output is disclosed. An implementation result may reveal an error in the text or expectation. It cannot establish a replacement answer. A correction to normative text, schema or expected bytes after freeze creates a new candidate identity.

## WCS2-014. Suite, runner and reports

Every case has exactly `id`, `operation`, `input`, `expected`, `requirements`, and `derivation`. The expected value is the complete output, including state, permit, budget results, receipts and digests where applicable. Case and path identities are unique. The suite manifest binds the candidate and pin, mandatory roles and requirements, exact case and review hashes, coverage inventory and frozen mutation catalog.

The runner compares canonical result bytes and contains no policy evaluator. Every mandatory case runs. A missing case, skip, duplicate result, malformed response, crash, timeout or output overflow fails qualification. Execution failure cannot count as a governance refusal or successful mutation detection.

The runner executes locally selected trusted programs in a minimal environment with bounded output, a default 30-second request timeout, an 8 MiB limit for each output stream and process-group cleanup. These controls are not a hostile-code sandbox. Installation may obtain pinned public dependencies. Scored execution uses no network, model, real service credential or adjacent repository.

Reports identify exact contract, suite, implementation and dependency hashes, claimed roles and profiles, runtime versions, every case and failure, mutation results, generated-input and state-interchange controls, reproduction commands and unsupported roles. Reports distinguish semantic consumer qualification, the reference host's serialized single-process qualification, documented host obligations and deployment assurance.
