# Governed work lifecycle

Identity: `seampoint.work-class/1.0.0-draft.2/lifecycle`. Status: `DRAFT_NOT_ADOPTED`, `APPARATUS_ONLY`. This document defines the common lifecycle used by every runtime profile in this candidate.

## LIFE-001. Records and claims

The lifecycle separates five facts: an organization authorized an exact deployment, a caller proposed an exact operation occurrence, the consumer issued a permit after applying current authority and shared limits, a host observed an attempted native dispatch, and the host later supplied evidence about the native effect. None of these records proves another. In particular, a proposal is not permission, a permit is not a dispatch, a dispatch acknowledgement is not an effect, and an effect is not proof that the operation was authorized.

Every lifecycle record is a closed object admitted under `lifecycle.schema.json`. Every record identifies the draft-2 candidate and the exact instance, occurrence, proposal, permit, dispatch, evidence or state that it concerns. A SHA-256 digest establishes the identity of the canonical record bytes. It does not authenticate the actor, host, connector or evidence source named by the record.

## LIFE-002. Profile family

The runtime profiles are cumulative. `LINEAR` admits linear work. `CHOICE_LOOPS` adds exclusive choice and bounded loops. `DEADLINES` adds activity deadlines to the preceding behavior. `PARALLEL_FANOUT` adds structured parallel work and frozen fan-out to all preceding behavior. A definition selects exactly one profile, and every `deploy` and `step` request supplies the corresponding role. An implementation may claim only the profile roles it implements and passes under the frozen suite.

| Profile | Runtime role |
|---|---|
| `LINEAR` | `LINEAR_WORK_RUNTIME` |
| `CHOICE_LOOPS` | `CHOICE_LOOP_RUNTIME` |
| `DEADLINES` | `DEADLINE_RUNTIME` |
| `PARALLEL_FANOUT` | `PARALLEL_FANOUT_RUNTIME` |

Any other admitted-enum pair is `ROLE_UNSUPPORTED` before definition or state checks. For an admitted pair, the request profile equals `definition.profile`. On `step`, the retained state's profile and role equal the request pair and the definition profile. An otherwise admitted mismatch is `BINDING_MISMATCH`; the consumer never interprets a definition or state through another profile.

The candidate excludes repeated fan-out expansion passes, dynamic fan-out, compensation, general cancellation, child-work invocation and distributed execution. A consumer refuses a definition that requires an excluded construct. It never substitutes a simpler profile or ignores an unsupported declaration.

## LIFE-003. Deployment

`deploy` admits one complete work-class definition, its exact digest, one profile, its corresponding runtime role, one instance identity, one deployment-authorization record, the complete organizational-authorization, correspondence, source-confirmation and policy-decision evidence records named by that deployment record, an available authorization clock and the exact initial deadline clocks. `deployment_authorization_subject_digest` is `digest("deployment-authorization-subject",deployment_authorization_without_authorization_evidence_digest)`. The authorization must bind the candidate pin, work-class digest, profile, role and instance. It must have status `AUTHORIZED`; `authorized_at` must be no later than `authorization_clock.observed_time`. A null `expires_at` declares no fixed upper bound. A nonnull expiry is exclusive and must be later than the authorization-clock instant; an authorization at or after that expiry yields `EVIDENCE_UNAVAILABLE`. The organizational-authorization evidence must have status `ACCEPTED`, use that subject digest as its subject, name the same organization, have `recorded_at` no later than the authorization clock, and have a nonnull exclusive expiry later than that clock. Its `authorization_scope` is the raw UTF-8 sorted unique set of the candidate pin, work-class digest, profile, role and instance identity. `authorization_evidence_digest` equals `digest("evidence",authorization_evidence)` and the deployment record contains that value. `deployment_authorization_digest` is `digest("deployment-authorization",deployment_authorization)` over the complete record. The deployment authorization also contains `correspondence_evidence_digest`, `source_confirmation_evidence_digest` and `policy_decision_evidence_digest`, and each equals `digest("evidence",record)` for the corresponding supplied record. Because those fields belong to the deployment-authorization subject, the organizational authorization covers the reviewed artifact and its stated residue, and it cannot be reused for a substituted or unreviewed artifact. The correspondence record meets every condition of the correspondence form of `check-evidence` for this definition; its own status and its nested review's status are `ACCEPTED`; and no residue row has disposition `PENDING`, while `UNSUPPORTED` and `EXCLUDED` rows remain retained and visible. The source-confirmation record has status `ACCEPTED`, subject digest `digest("work-class-source",definition.source)` and `scope_ids` equal to the definition's complete source-obligation list. The policy-decision record has status `ACCEPTED` and subject digest `digest("work-class-definition",definition)`. Each of the three records has `recorded_at` no later than the authorization clock. The four deployment evidence records have four distinct evidence identifiers; one person may hold several remits, but one record cannot serve two kinds. A record, nested review or residue row that is pending, rejected or deferred yields `EVIDENCE_UNAVAILABLE`; a digest, subject, source, scope, partition, coverage, time or identifier-distinctness mismatch yields `BINDING_MISMATCH`. These checks follow the organizational-authorization checks and precede `initial_clocks`. Within them every `BINDING_MISMATCH` condition of the three records precedes every `EVIDENCE_UNAVAILABLE` condition, so a deployment with faults of both kinds is refused `BINDING_MISMATCH`. The evidence records name the definition and its source, never the deployment authorization, so the bindings remain acyclic. These projections bind the records without a cycle. Pending, rejected, deferred, missing or mismatched evidence yields `EVIDENCE_UNAVAILABLE` or `BINDING_MISMATCH` as applicable. The authorization clock is required for every deployment and cannot be replaced by ambient time. A digest match does not establish that the organization, authorizer or clock source is authentic; the host supplies those external facts under `EXTERNAL-DEPENDENCIES.md`.

A successful deployment creates the initial state for that exact instance. It activates the root occurrence and retains the complete deployment-authorization record, its subject and complete-record digests, the complete organizational-authorization, correspondence, source-confirmation and policy-decision evidence records, their evidence digests, the exact authorization clock and the organization identity. Restart recomputes every digest, time relation and binding. The deployment also installs any deadline state that begins at root activation and creates no proposal, permit, reservation, dispatch or outcome. `initial_clocks` contains exactly one available record for each distinct clock source required by a root deadline, sorted by source; lower profiles and roots without deadlines require an empty array. A missing source is `EVIDENCE_UNAVAILABLE`; an extra or mismatched source is `DEPENDENCY_MISMATCH`. The authorization clock and an initial deadline clock may contain equal records but remain distinct input fields with distinct purposes. The root activation trigger is `digest("deployment-activation",{deployment_authorization_digest,instance_id,occurrence_id})`. For each root deadline, the consumer constructs the persisted activation record from the initial clock for its source under LIFE-014. If that record already satisfies the deadline predicate, deployment returns `CLOCK_INVALID`; this prevents an already expired root from entering state without an expiry decision. An authorization that names another instance is `DEPENDENCY_MISMATCH`; other mismatched authorization or evidence subjects are `BINDING_MISMATCH`. Deployment does not authorize a native operation. A malformed request that prevents profile and role admission returns the generic shape refusal. After profile and role are admitted, any failed deployment returns the closed lifecycle deployment refusal with those exact identities, the selected code and an empty path; it returns no initial state. The pure `deploy` operation calculates this initial state without consulting a host namespace. Before accepting any `step`, a host must atomically install that state as the one authoritative root for the exact organization and instance under LIFE-020.

## LIFE-004. Operation and occurrence identity

Every native operation belongs to one exact occurrence. The occurrence contains the candidate pin, work-class digest, instance identity, step, ordinal, sorted direct predecessor occurrence identities, complete enclosing path and object key where fan-out applies. Its identifier is `digest("occurrence",{specification_pin,work_class_digest,instance_id,step_id,ordinal,predecessor_occurrence_ids,enclosing,object_key})`. The first linear operation therefore has an occurrence identity before any loop, branch or fan-out exists; its predecessor list is empty.

An enclosing path lists segments from outermost to innermost. A `LOOP` segment has null branch and object values. A `BRANCH` segment has a nonnull branch and null object. A `FANOUT` segment has a null branch and nonnull typed object key. If the path contains a fan-out segment, the occurrence's top-level `object_key` equals the innermost fan-out segment's key; otherwise it is null. Implementations compare the complete identity. An act, completion, permit or effect for another instance, step, ordinal, pass, branch or object cannot satisfy the occurrence.

## LIFE-005. Step transaction

`step` accepts the exact definition and digest, profile and role, one complete prior work state and digest, and one event. The event is exactly one of `PROPOSE`, `DISPATCH_OBSERVED`, `EFFECT_OBSERVED` or `CLOCK`. Each event binds the expected prior work-state revision and digest. An event cannot carry fields belonging to another variant. The consumer validates the request envelope, selected version and role, definition, state binding and event shape before applying stateful rules.

After exact replay and binding checks, instance status controls new work. `PROPOSE` requires instance status `ACTIVE`; a new proposal against `COMPLETE` or `STOPPED` is `INSTANCE_NOT_ACTIVE` and leaves all work and budget states unchanged. `DISPATCH_OBSERVED` remains admissible so an attempted or prohibited dispatch can be retained, but a host must not initiate a new dispatch after either terminal instance status. `EFFECT_OBSERVED` remains admissible for reconciliation and cannot reopen routing. `CLOCK` remains admissible to retain clock evidence and expire any pending sibling deadlines, but it cannot create a successor from a complete or stopped instance. These rules do not alter exact replay, which is checked first.

The returned transition contains one decision receipt, the complete next work state, every affected shared-budget result and a digest over the complete transaction. The receipt's `decision_id` and the result's `decision_digest` are the same value: `digest("decision-receipt", receipt)` over the complete receipt with `decision_id` omitted. The reference host serializes access to the work state and every affected shared budget, computes the full transition, and commits all returned state before any native dispatch. A work-state change and the budget-state changes in one successful proposal or effect transition are one atomic unit. The pure adapter describes the transition; the single-process reference host qualifies only the stated serialized commit behavior.

## LIFE-006. Refusal and admitted decision

An admission refusal means that the supplied request, definition, state, event or binding was not admitted. A stateful refusal returns the exact supplied work state and all supplied budget states unchanged. It creates no permit, reservation or decision receipt. The host may retain the refusal outside governed state for operations telemetry, but that retention cannot change the conformance result.

An admitted policy decision means that the event was well formed and changed the facts known to the work instance. The consumer records the event identifier and canonical event digest in work state, records a decision receipt, and increments the work-state revision even when the disposition is `WITHHELD`, `STOPPED`, `FAILED`, `EXPIRED` or `DISPUTED`. The work state is an execution checkpoint with exact commitments to the event preimages; it is not the complete audit package. The host retains the complete canonical request and response bytes in the event log required by LIFE-019 and `EXTERNAL-DEPENDENCIES.md`. A policy decision creates no permit unless its disposition is `PERMITTED`. A policy refusal and an admission refusal are different results. Every decision carries a closed `details` list. The list has at most one value of each kind and uses this order when present: `AUTHORITY`, `SEPARATION`, `BUDGET`, `DISPATCH`, `EFFECT`, `CLOCK`, `DEADLINE`, `ROUTE`, `LABEL`, `LIMIT`. Authority, separation and budget withholdings carry their corresponding detail. Dispatch observations carry `DISPATCH`. Effect observations carry `EFFECT` and also carry `ROUTE`, `LABEL`, or `LIMIT` when that same transition selects a route or stops on a label or limit. An effect observation whose transition applies a reservation registry result also carries `BUDGET`, with that registry digest, receipt digest and receipt reasons. Clock events carry `CLOCK` and also carry `DEADLINE`, `ROUTE`, or `LIMIT` when that same transition expires work, routes, or stops. A decision for which none of these facts applies has an empty list. `reason_codes` is the raw UTF-8 sorted unique union required by the included details and the applicable transition rule. A consumer rejects a missing, duplicate, out-of-order or incompatible detail, reason or state combination as `STATE_INVALID` on restart.

The exact decision-reason mapping is exhaustive:

| Event and admitted result | Exact contribution to `reason_codes` |
|---|---|
| `PROPOSE/PERMITTED` | empty |
| Authority `PROPOSE/WITHHELD` | `AUTHORITY_REQUIRED`, the authority refusal code and every authority refusal reason |
| Cross-occurrence actor `PROPOSE/WITHHELD` | `SEPARATION_VIOLATED` |
| Budget `PROPOSE/WITHHELD` | `BUDGET_WITHHELD` and every reservation receipt reason |
| Initial `PROPOSE/STOPPED` on actuation limit | `LIMIT_EXCEEDED` |
| Any `DISPATCH_OBSERVED` decision | exactly the `DISPATCH` detail's `reasons` |
| Any non-`DUPLICATE` effect classification whose budget receipt decision is `EFFECT_DISPUTED` | add `BUDGET_EFFECT_DISPUTED` and every reservation receipt reason to the classification-specific reasons |
| Any conclusive effect classification for an occurrence already `BLOCKED_DISPUTE`, with no disputed budget result | add `DEPENDENCY_DISPUTED` to the classification-specific reasons |
| `EFFECT_OBSERVED` with `MATCHED` or `FAILED` and no stop condition and no disputed budget result | empty |
| `EFFECT_OBSERVED/UNKNOWN` | `UNKNOWN_OUTCOME` |
| `EFFECT_OBSERVED/NO_EFFECT_ESTABLISHED` | `NO_EFFECT_ESTABLISHED` |
| `EFFECT_OBSERVED/UNEXPECTED` | `UNEXPECTED_EFFECT` |
| `EFFECT_OBSERVED/CONFLICTING` | `CONFLICTING_EFFECT` |
| `EFFECT_OBSERVED/FOREIGN` | `FOREIGN_EFFECT` |
| `EFFECT_OBSERVED/LATE_MATCHED` | `LATE_EFFECT` |
| `EFFECT_OBSERVED/LATE_AFTER_RELEASE` | `LATE_EFFECT_AFTER_RELEASE` |
| `EFFECT_OBSERVED/DUPLICATE` | `DUPLICATE_EVIDENCE` |
| Declared native failure with `failure_behavior:STOP` | add `DECLARED_FAILURE` |
| Invalid choice label | add `LABEL_INVALID` |
| Loop-pass stop | add `LOOP_BOUND_REACHED` |
| Fan-out duplicate-set or empty-set stop | add `FANOUT_SET_DUPLICATE` or `FANOUT_EMPTY` |
| Structural or actuation limit stop | add `LIMIT_EXCEEDED` |
| Effect-triggered activation deadline failure | add every applicable `ACTIVATION_CLOCK_UNAVAILABLE`, `DEADLINE_ALREADY_DUE` and `DEADLINE_TIME_OVERFLOW` |
| `CLOCK/CLOCK_RECORDED` with unavailable or conflicting input | `CLOCK_UNAVAILABLE` |
| Available `CLOCK/CLOCK_RECORDED` with no due work | empty |
| Normal `CLOCK/EXPIRED` | empty |
| `CLOCK/STOPPED` | exactly the `DEADLINE` detail's `reasons`, plus `LIMIT_EXCEEDED` exactly when a `LIMIT` detail is present |

Rows that say “add” combine with the effect-classification row. The `DUPLICATE` row takes precedence and fixes the complete set to `DUPLICATE_EVIDENCE`, including when its idempotent reservation receipt reports an already retained dispute. Every other row fixes the complete set. No other reason code is admitted for these transitions. `details` carry the underlying records even when the exact reason set is empty.

The occurrence and instance consequences are fixed:

| Decision | Occurrence consequence | Instance consequence |
|---|---|---|
| `WITHHELD` | active occurrence remains `ACTIVE` | remains `ACTIVE` |
| `PERMITTED` | becomes `PERMITTED`; permit and proposal retained | remains `ACTIVE` |
| `DISPATCH_REFUSED` for a safe `NOT_SENT` attempt with no accepted acknowledgement, including changed arguments that were definitively not sent | remains `PERMITTED` when it was dispatchable; otherwise retains its prior status | retains its prior status |
| `DISPATCH_REFUSED` for connector `REJECTED` | remains `PERMITTED` when it was dispatchable, but its dispatch record prevents another attempt; otherwise retains its prior status | retains its prior status pending effect or explicit no-effect evidence |
| `DISPATCH_RECORDED` or `ACKNOWLEDGED` | becomes `DISPATCHED` | remains `ACTIVE` |
| disputed dispatch | a `PERMITTED` occurrence becomes `OUTCOME_UNKNOWN`; a `BLOCKED_DISPUTE` or completed occurrence retains its prior status | retains its prior instance status |
| `OUTCOME_RETAINED` for unknown effect | an unresolved active occurrence becomes or remains `OUTCOME_UNKNOWN`; a completed occurrence remains unchanged | an `ACTIVE` instance remains `ACTIVE`; a terminal instance remains unchanged |
| `DISPUTED` governed effect | an unresolved occurrence that is not already `BLOCKED_DISPUTE` becomes `OUTCOME_UNKNOWN` for an inherently disputed classification (`UNEXPECTED`, `CONFLICTING` or `LATE_AFTER_RELEASE`), including when its budget reconciliation is also disputed, or `BLOCKED_DISPUTE` for a conclusive `MATCHED`, `FAILED` or `NO_EFFECT_ESTABLISHED` effect whose budget reconciliation alone is disputed; a `BLOCKED_DISPUTE` occurrence remains `BLOCKED_DISPUTE`; an `UNKNOWN` classification with a disputed budget result leaves an unresolved occurrence that is not `BLOCKED_DISPUTE` `OUTCOME_UNKNOWN`; dependent descendants are blocked; a completed occurrence remains unchanged | an `ACTIVE` instance remains `ACTIVE`; a `COMPLETE` or `STOPPED` instance remains unchanged |
| `DISPUTED` foreign effect | current occurrences do not change | retains its prior status |
| `COMPLETED`, `FAILED`, or `OUTCOME_RETAINED` for a conclusive effect under the exact LIFE-010 disposition mapping | applies the exact LIFE-010 work consequence; a dependency-blocked occurrence remains blocked | applies a route only where LIFE-010 permits one; becomes `COMPLETE` only after terminal closure with no active occurrence or unresolved obligation |
| `EXPIRED` for a due dependency-blocked deadline | deadline becomes `EXPIRED`; occurrence remains `BLOCKED_DISPUTE` and its directly owning obligation, if any, remains `BLOCKED` | retains its prior instance status; no expiry route, join or successor is applied |
| Normal `EXPIRED` for an eligible occurrence | moves the occurrence to `completed` with disposition `EXPIRED` | applies the declared expiry target; becomes `COMPLETE` only after terminal closure with no active occurrence or unresolved obligation |
| `STOPPED` | the triggering occurrence closes when an effect or expiry established the stop; for an actuation-limit stop at proposal, the occurrence remains `ACTIVE` because no effect occurred; a would-be successor is never created for a structural preflight stop | becomes `STOPPED` |
| late dispatch or effect | retained without reactivating or rerouting a closed occurrence | `COMPLETE` or `STOPPED` never reverts |

An occurrence removed from `active` appears exactly once in `completed`. An outcome that leaves an occurrence unresolved does not move it. A permit is dispatchable only while its occurrence is `PERMITTED`, the permit has not expired or been superseded, and retained dispatch records allow an attempt under LIFE-009. The instance status vocabulary is `ACTIVE`, `COMPLETE`, and `STOPPED`; unresolved and disputed conditions remain visible in occurrence, obligation, outcome and reservation state rather than an undefined summary status.

For a request with several independent faults, the consumer applies this precedence: transport and canonical-byte admission; protocol, candidate and role selection; closed schema; definition and state identity; event replay; event-to-instance and event-to-occurrence binding; event-kind prerequisites; the retained proposal-count ceiling; prior-effect selection and value binding; current authority, including its required clock and observation availability; cross-occurrence actor separation; the initial-proposal actuation ceiling; shared-budget revision and policy; effect-carrier classification and declared route selection; effect- or clock-driven structural composition preflight. A higher-precedence fault determines the response. The actuation ceiling is not evaluated on permit renewal. A ceiling failure retains the successful authority result but does not evaluate or commit a supplied registry transition. The suite contains competing-fault cases for every precedence boundary used in qualification. COMP-002 defines precedence when several declared limits fail within one selected closure.

## LIFE-007. Proposal

A `PROPOSE` event identifies one active occurrence and supplies the exact native request, executor binding, credential identities, complete current authority input, required registry-scoped shared-budget inputs with expected revisions, accepted clock revision and observation digests. The native request identifies its interface and operation and carries the complete typed field set. The proposal digest binds all of these values together with the instance and occurrence. An occurrence or instance mismatch is `BINDING_MISMATCH` after replay and state identity admission. For every `FANOUT` segment in the occurrence's enclosing path, the definition resolves that construct's exact `object_request_field`; the native request contains that field once with the construct's `object_type_ref` and a value equal to the segment's retained object key. All such field names are distinct along the path. A missing, duplicated, wrongly typed or unequal value is `BINDING_MISMATCH` before authority or reservation evaluation. This prevents a proposal for frozen object A from operating on object B even when a broad authority grant would otherwise cover B.

Before current authority evaluation, the consumer resolves every prior-effect binding declared by the active step under COMPOSITION 2.3. For each unique eligible ancestor, it resolves the exact retained governed `MATCHED` outcome whose native-evidence digest established the ancestor's `SUCCEEDED` completion. The source evidence field occurs exactly once in `native_evidence.actual_fields`; its typed value equals the target field in the current native request by exact nominal type and canonical scalar value. No eligible ancestor, including a source whose establishing outcome is missing or disputed, is `PREREQUISITE_MISSING`. Multiple eligible ancestors, a missing or duplicate evidence or request field after selection, a changed type or an unequal value is `BINDING_MISMATCH`. The checks run in binding-identifier order, and the first failure determines the result. All are admission checks, so a refusal changes neither work nor budget state.

The consumer first determines whether this is an initial proposal or a permit renewal. An initial proposal names an occurrence with status `ACTIVE` and no retained permit or unresolved outcome. A renewal names an occurrence with status `PERMITTED`, the latest permit for that occurrence, an exact unchanged native request and no dispatch record that consumed or may have reached the connector. Renewal eligibility uses the latest retained available lifecycle clock for the permit source. That retained instant must be at or after the permit's exclusive expiry. Before that point, or without a retained available clock that establishes it, renewal is `PREREQUISITE_MISSING`. After retained expiry is established, the new authority input is evaluated normally; its current clock may be unavailable and produce the ordinary admitted authority withholding. A renewal after any attempt with status `REJECTED`, `SENT`, or `UNKNOWN`, after any accepted acknowledgement or disputed dispatch, or with changed operation fields is `PREREQUISITE_MISSING` or `BINDING_MISMATCH` as applicable. A safe `NOT_SENT` attempt remains eligible even when its acknowledgement is `REJECTED` because that acknowledgement does not mean the attempt status was `REJECTED`. The consumer then recomputes the authority judgment from the supplied authority input for either path. A caller-supplied status or an old readiness receipt cannot replace that evaluation. The active step has exactly one authority requirement, and that identifier equals `authority_input.envelope.id`. The lifecycle definition has one exact authority projection: `{schema:"seampoint.work-class/1.0.0-draft.2/authority-work-class",id,revision,types,steps}`. It copies the definition id and revision; copies the sorted unique set of every authority-supported type referenced by a proposal-capable step field; and copies every proposal-capable step as `{id,operation,interface,executor_role,fields,scope_fields,required_credentials}`. Projected types and steps sort by id in raw UTF-8 order. Every copied proposal field must use an authority-supported scalar type, and no unreferenced type or structural step enters the projection. `authority_input.work_class` equals that projection. Both `authority_input.proposal.work_class_digest` and `authority_input.envelope.work_class_digest` equal `digest("authority-work-class",projection)`. The authority source ID and revision equal the lifecycle source ID and revision, and the raw UTF-8 sorted unique authority obligation IDs equal the lifecycle source's obligation list with no addition or omission; the authority source retains each obligation's supplied text as externally reviewed source evidence. Lifecycle executor `participant_id` identifies exactly one declared work-class participant. Its role equals both that participant's role and the active step's executor role; every declared participant kind is eligible when these bindings and the authority rules succeed. The participant ID also equals authority proposal executor `actor`, and the lifecycle executor role equals the authority executor role. `executor.binding_digest` is `digest("executor-binding",{actor,role,principal,occupancy})` over the complete authority executor record. The proposal's credential identifiers are the raw UTF-8 sorted identifiers of the complete authority credentials. Its observation digests are the raw UTF-8 sorted `digest("authority-observation",observation)` values of the complete authority observations. The lifecycle `clock_revision` identifies an accepted available lifecycle clock whose source equals the authority clock source and whose observed time equals the authority clock instant. Because AUTH-005 requires that current clock for every readiness result, a successful proposal always supplies a nonnull revision. Null is representable only on an authority-withheld proposal whose selected clock is unavailable. The authority subject must otherwise match the candidate, instance, occurrence, step, operation, interface, native fields and proposal. Every applicable authority check must succeed, including current revocation and validity checks.

After authority and every declared actor-separation check succeed, the consumer applies at most one reservation transition against one complete reservation registry. The active step's sorted `shared_budgets` equals the authority result's sorted `required_budgets`. An empty set requires no budget input. A nonempty set requires exactly one budget input `{registry_digest,affected_anchors,expected_revision,request}`. Its `affected_anchors` equals that required set, and the registry configuration contains exactly one slot for every required anchor; unrelated registered slots may remain. Every affected budget policy's settlement provider/source pair equals the step completion carrier's effect provider/source pair, and every no-effect provider/source pair equals the carrier's no-effect pair. An incompatible set is `UNSUPPORTED_RELATION` before reservation evaluation and leaves work and registry state unchanged. Its registry digest equals both `digest("reservation-registry",request.state.core.configuration)` and `request.host_evidence.registry_digest`. Its expected revision equals both `request.event.expected_revision` and `request.state.core.revision`. The embedded event is `RESERVE` for an initial proposal and `RENEW` for a renewal. A renewal names the exact reservation retained by the prior permit; preserves its original request, proposal fields, occurrence, contributions and creation time; and supplies the fresh complete authority input and current histories required by RES-006. The embedded identifier is `digest("lifecycle-reservation-event",{instance_id:event.instance_id,lifecycle_event_id:event.event_id,lifecycle_event_kind:"PROPOSE",reservation_event_kind,registry_digest})`, where `reservation_event_kind` is `RESERVE` or `RENEW`. This makes the event unique in the shared registry even when another work instance uses the same local lifecycle event identifier. It carries the lifecycle's complete authority input. Its authority proposal equals the reservation native-request projection `{work_class:definition.id,instance:event.instance_id,occurrence:event.occurrence.occurrence_id,step:event.occurrence.step_id,operation:event.native_request.operation,interface:event.native_request.interface,fields:event.native_request.fields}`. Its event clock is the exact accepted lifecycle clock selected by `clock_revision` and used by the authority input; the embedded clock source, instant and revision must agree. A proposal whose required anchors span reservation registries is outside this candidate and cannot be represented by the closed single-registry input. Calling the registry transition once may change several budgets. The consumer never calls it again per anchor.

The lifecycle maps authority evaluator results without guessing. `SCHEMA_INVALID`, `ARTIFACT_ENCODING_INVALID`, `ARTIFACT_NONCANONICAL`, `TYPE_INVALID`, `INPUT_INVALID`, `LIMIT_EXCEEDED`, `VERSION_UNSUPPORTED`, `DEPENDENCY_MISMATCH`, `UNSUPPORTED_RELATION`, `REFERENCE_INVALID` and `BINDING_MISMATCH` remain admission refusals with the same code and no state change. `EVIDENCE_UNAVAILABLE`, `ACT_CONFLICT`, `GATE_REQUIRED`, `ACT_NOT_AUTHORIZED`, `ACT_NOT_ACCEPTED` and `AUTHORITY_NOT_ESTABLISHED` are admitted policy withholdings. A withholding stores `digest("authority-result",authority_refusal)` in the proposal record and decision receipt. Its sorted reason codes are the union of `AUTHORITY_REQUIRED`, the authority refusal code and every authority refusal reason. Its `AUTHORITY` detail carries the refusal code, its reasons and its exact `failed_checks`, so the decision record names each failed check; the detail of a successful authority result has empty `failed_checks`. A successful readiness result is retained by the same digest kind.

After current authority succeeds, the consumer retains the complete readiness result and projects every act selected by it to `{act_digest,act}`, where `act` is the complete closed authority-act record. It sorts those authority-act bases by act digest. Every digest in the result resolves exactly once to a complete act in the current authority input, no other act enters the projection, and restart can recompute each act digest from its preimage. For each prior-actor separation declared by the active step, in requirement-identifier order, the consumer selects the unique eligible completed ancestor under COMPOSITION 2.3 and its exact establishing permit. It resolves exactly one prior authority-act basis whose complete act has `prior_act_kind` from that permit and exactly one current authority-act basis whose complete act has `current_act_kind`. No eligible prior occurrence or selected act is `PREREQUISITE_MISSING`; multiple eligible occurrences or acts is `BINDING_MISMATCH`. If the exact actor identifiers are equal, the consumer records an admitted `WITHHELD` proposal with `SEPARATION_VIOLATED`, the successful authority-result digest and one `SEPARATION` detail containing the complete readiness result plus both complete self-verifying act bases for that first failing comparison. It does not evaluate later separation requirements, creates no permit or reservation and leaves every budget unchanged. Distinct actors satisfy the relation. Authenticating the two actor identifiers as different real people remains the host boundary in `EXTERNAL-DEPENDENCIES.md`.

The reservation transition is evaluated on a clone. An admission refusal from that transition is a lifecycle admission refusal and leaves both work and registry state unchanged. A reservation `WITHHELD` result commits that registry's complete withholding receipt and next state together with one lifecycle proposal record and the lifecycle `WITHHELD` decision; it creates no reservation or permit. The proposal record has disposition `WITHHELD`, binds the successful authority-result digest, contains the one registry withholding receipt digest, has a null permit digest, and has a null prior-permit digest for an initial proposal or the prior permit digest for a renewal. Its lifecycle reason codes are the sorted union of the reservation receipt's reasons and `BUDGET_WITHHELD`. A `RESERVED` initial result or `RENEWED` renewal result commits the registry state, proposal record, new permit and work decision together. No dry-run result or partial state is exposed.

Every admitted authority, separation or budget-policy withholding appends one proposal record with disposition `WITHHELD`; every successful proposal appends one with disposition `PERMITTED`. An authority withholding records its authority-refusal digest, an empty reservation-receipt digest array, a null permit digest, and leaves the registry unchanged. A separation withholding records the successful authority-result digest, an empty reservation-receipt digest array, a null permit digest and the exact `SEPARATION` detail, and leaves the registry unchanged. A budget withholding records the successful authority-result digest and the one registry withholding receipt digest, commits the work and registry withholding receipts together, and creates no new or extended reservation. All three withholding forms record a null `prior_permit_digest` for an initial proposal or the prior permit digest for a renewal. If an input or revision is invalid, the consumer returns an admission refusal and appends no proposal record, leaving work and registry state unchanged. If all checks pass, the consumer creates the proposal record, creates or renews the reservation within the one registry, creates one permit and records one `PERMITTED` receipt in a single transition. A successful initial proposal records a null prior permit; a successful renewal records the superseded permit. A renewal does not increment activation or actuation counters and does not create another exposure. A withheld renewal does not supersede or extend the prior permit or reservation.

## LIFE-008. Permit

A permit authorizes at most one native dispatch for one exact proposal and occurrence. Its `permit_id` is `digest("permit", permit)` over the complete permit with `permit_id` omitted. `proposal_digest` is `digest("proposal",event)` over the complete admitted `PROPOSE` event. `authority_result` is the complete recomputed readiness result, `authority_result_digest` is `digest("authority-result",authority_result)`, and `authority_evidence_digest` is that result's exact evidence digest. The executor, credential IDs and observation digests equal the projections in LIFE-007. `authority_act_bases` is the complete selected-act projection defined there. `prior_effect_bases` has one row for every declared prior-effect binding, sorted by binding identifier. Each row retains the binding identifier, source occurrence, establishing permit and native-evidence digests, source and target fields and exact typed value. The permit and native-evidence digests remain stable if later conflict evidence makes the source outcome disputed. `separation_bases` has one row for every satisfied prior-actor separation, sorted by requirement identifier. Each row retains the relation, source and current occurrences and the complete prior and current authority-act bases; the nested acts expose both actor identifiers and bind them to recomputable act digests. `clock_source` and `clock_revision` identify the accepted authority clock for every permit. `expires_at` is always nonnull and exclusive. It is the proposal clock plus the active step's declared `permit_seconds`, or the earlier returned reservation expiry when a shared budget applies. Calendar overflow is `LIMIT_EXCEEDED` and creates no permit or state change. When no shared budget applies, `budget_revisions` is empty. Otherwise the budget array has one row: `registry_digest` and `affected_anchors` identify the single registry result; `revision` is its committed post-`RESERVE` or post-`RENEW` revision; `reservation_id` is the reservation created or renewed by that receipt; and `receipt_digest` identifies that exact receipt. The permit clock also identifies the clock used by the embedded reservation event. `supersedes_permit_digest` is null for an initial permit and names the immediately preceding permit for a renewal. Every field is checked on restart. Changing any bound value produces a different request outside the permit.

The permit becomes dispatchable only after the host commits the complete returned work and budget state. The adapter's successful result describes the state to commit. It does not prove that the host performed the commit. A host that cannot confirm that complete commit must not dispatch. Commit failure leaves the prior authoritative states in force and the proposed native request undispatched.

A permit is not transferable to another instance, occurrence, executor, connector request or retry with changed arguments. The candidate uses the authority and observation snapshot established by the successful proposal until the permit's exclusive expiry. The organization's deployment authorization of the exact work-class definition and candidate accepts that declared finite snapshot policy. A later revocation or changed observation prevents a new proposal or renewal when the current checks detect it, but it does not erase a still-valid committed permit, reservation, dispatch record or later effect evidence. A host that honours such a revocation or changed observation declines to dispatch under the committed permit; the permit expires unused, and a later renewal under LIFE-007 evaluates current authority. An organization that requires a shorter interval must declare a shorter step duration. After expiry the host must obtain a new proposal and current evaluation rather than revalidate or extend the old permit implicitly.

## LIFE-009. Dispatch observation

A `DISPATCH_OBSERVED` event supplies the complete committed permit, the exact native request presented to the connector, the connector identity and binding, one attempt record, one acknowledgement record and the clock revision used to validate the dispatch timeline. The consumer checks the committed permit and its digest before considering the connector fields. A permit absent from the admitted work state is `PREREQUISITE_MISSING`. The event revision identifies the latest retained available lifecycle clock for `permit.clock_source`. A missing, nonlatest or wrongly sourced revision is `CLOCK_INVALID`. The state contains the retained available permit clock named by `permit.clock_source` and `permit.clock_revision`. `attempt.attempted_at` is no earlier than that issuance clock and no later than the selected dispatch clock; a value outside that closed interval is `CLOCK_INVALID`. Permit expiry is evaluated against `attempt.attempted_at`, with an attempt at or after the exclusive expiry adding `PERMIT_EXPIRED`. A dispatch may be reported after permit expiry without that reason when its exact attempt occurred before expiry and the other permission conditions held. This preserves later effect reconciliation for a timely native attempt while preventing a stale pre-expiry clock from authorizing a later attempt. The host authenticates the clock and attempt record; the consumer does not use ambient time.

The dispatch table supplies the base reason set for every attempt and acknowledgement pair, including rows later modified by another fact. A row marked `none` supplies no base reason. A native request mismatch adds `NATIVE_ARGUMENT_MISMATCH`; an expired permit adds `PERMIT_EXPIRED`; a superseded permit adds `PERMIT_SUPERSEDED`; and a terminal instance, closed occurrence or occurrence status other than `PERMITTED` adds `LATE_OR_PROHIBITED_DISPATCH`. The acknowledgement-update exception below reuses the original attempt's permission facts and does not add a current-state reason merely because the earlier attempt already advanced or completed the occurrence. The final `reasons` list is the raw UTF-8 sorted unique union. When the attempt is `NOT_SENT` and acknowledgement is not `ACCEPTED`, the consumer records `DISPATCH_REFUSED`; it never marks either request as sent. The exact permit remains dispatchable only when it is the unsuperseded head, unexpired, eligible for the instance and occurrence, and no other retained attempt consumed it. Every combination that may have reached the connector, meaning attempt `SENT` or `UNKNOWN` or acknowledgement `ACCEPTED`, records `DISPUTED` when arguments changed, permission expired, the permit was superseded, the instance was terminal, or the occurrence was closed or no longer `PERMITTED`. A changed request with attempt `REJECTED` and no accepted acknowledgement also records `DISPUTED`: connector rejection does not prove that the changed operation had no effect. These disputed rows consume the permit and retain the exact attempted request for effect reconciliation. A `PERMITTED` occurrence becomes `OUTCOME_UNKNOWN`; a `BLOCKED_DISPUTE` occurrence remains blocked, and a completed occurrence is not recreated. A matching request with connector attempt `REJECTED` and no accepted acknowledgement follows the matching-request table when timely; after expiry, supersession, terminal instance or any occurrence status other than `PERMITTED` it records `DISPATCH_REFUSED` and cannot restore dispatchability. The conforming reference host compares the request and commits the unsuperseded permit before invoking the connector, so its own changed-argument call produces only the safe `NOT_SENT` row.

`attempt.request_digest` is `digest("dispatch-native-request",{instance_id,occurrence_id,interface,operation,fields})` using the event instance, permit occurrence and exact lifecycle native request. A different attempt digest is `BINDING_MISMATCH`, even when the separately supplied native request matches. `connector.binding_digest` equals `digest("connector-binding",{id,version})` for the exact connector record with the digest omitted. The consumer recomputes that binding. `dispatch_attempt_digest` is `digest("dispatch-attempt",{permit_id,native_request,connector,attempt})`. It identifies the one physical-attempt claim independently of the acknowledgement or event that reported it. Every dispatch record retains both this stable attempt digest and its complete `dispatch_digest`; the latter continues to identify the exact observation record. Whether this connector is the authentic host-configured endpoint for the governed interface and operation remains a host obligation.

An acknowledgement with status `NONE` has null `reference` and `observed_at`. An `ACCEPTED`, `REJECTED`, or `UNKNOWN` acknowledgement has a nonnull reference and observation time. Its observation time is no earlier than `attempt.attempted_at` and no later than the selected retained clock. A recorded acknowledgement before the attempt is `INPUT_INVALID`; one after the selected clock is `CLOCK_INVALID`. These checks precede the dispatch result table.

The complete timely result table for a matching native request on an active instance and occurrence is:

| Attempt | Acknowledgement | Decision | Reasons | Occurrence after decision | Permit may support a fresh attempt |
|---|---|---|---|---|---|
| `NOT_SENT` | `NONE`, `REJECTED`, or `UNKNOWN` | `DISPATCH_REFUSED` | `NATIVE_NOT_SENT` | `PERMITTED` | yes |
| `NOT_SENT` | `ACCEPTED` | `DISPUTED` | `DISPATCH_EVIDENCE_CONFLICT` | `OUTCOME_UNKNOWN` | no |
| `SENT` | `ACCEPTED` | `ACKNOWLEDGED` | none | `DISPATCHED` | no |
| `SENT` | `NONE` | `DISPATCH_RECORDED` | none | `DISPATCHED` | no |
| `SENT` | `REJECTED` | `DISPATCH_RECORDED` | `ACKNOWLEDGEMENT_REJECTED` | `DISPATCHED` | no |
| `SENT` | `UNKNOWN` | `DISPATCH_RECORDED` | `DISPATCH_STATUS_UNKNOWN` | `DISPATCHED` | no |
| `REJECTED` | `NONE`, `REJECTED`, or `UNKNOWN` | `DISPATCH_REFUSED` | `NATIVE_DISPATCH_REJECTED` | `PERMITTED` | no |
| `REJECTED` | `ACCEPTED` | `DISPUTED` | `DISPATCH_EVIDENCE_CONFLICT` | `OUTCOME_UNKNOWN` | no |
| `UNKNOWN` | `ACCEPTED` | `ACKNOWLEDGED` | none | `DISPATCHED` | no |
| `UNKNOWN` | `NONE`, `REJECTED`, or `UNKNOWN` | `DISPATCH_RECORDED` | `DISPATCH_STATUS_UNKNOWN` | `DISPATCHED` | no |

An attempt identifier is unique within one permit. After event replay, permit and request binding, and acknowledgement timeline checks, the consumer recognizes an acknowledgement update before applying current occurrence or instance dispatch eligibility. The update reuses an earlier exact `dispatch_attempt_digest` only when the complete retained native request, connector and attempt are byte-identical, its retained acknowledgement was `NONE` or `UNKNOWN`, and the new acknowledgement is `ACCEPTED` or `REJECTED`. It records another dispatch observation with the same stable attempt digest and a new complete dispatch digest, but never invokes the connector again. The consumer evaluates the attempt and new acknowledgement through the table using the permission, request-match, expiry and supersession facts recorded for the original attempt; it does not add `LATE_OR_PROHIBITED_DISPATCH` merely because that attempt already changed the occurrence to `DISPATCHED`, the occurrence later completed or expired, or the instance later stopped. The current occurrence and instance status remain unchanged. An original `NOT_SENT` or `REJECTED` attempt followed by `ACCEPTED` remains `DISPUTED/DISPATCH_EVIDENCE_CONFLICT`; a prior argument mismatch or other original disqualification remains in the updated reason set. Changed request, connector or attempt bytes give `BINDING_MISMATCH`; an unchanged or already conclusive acknowledgement under a new event gives `PREREQUISITE_MISSING`. A conforming host makes a fresh attempt only when every earlier matching-request attempt for the permit was `NOT_SENT`; `REJECTED`, `SENT`, `UNKNOWN` or disputed evidence consumes the permit for native dispatch. When an attempt under a fresh identifier on a consumed permit is nevertheless reported with attempt `SENT` or `UNKNOWN` or acknowledgement `ACCEPTED`, the consumer retains it as a `DISPUTED` dispatch with `LATE_OR_PROHIBITED_DISPATCH` for later effect reconciliation. A `PERMITTED` occurrence becomes `OUTCOME_UNKNOWN`, and every other occurrence status is unchanged. A fresh attempt reported `NOT_SENT` with no accepted acknowledgement on a consumed permit is `PREREQUISITE_MISSING`, because nothing reached the connector. A fresh attempt reported `REJECTED` with no accepted acknowledgement on a consumed permit is admitted, because a rejection may have reached the connector: with a matching request it records `DISPATCH_REFUSED` with `LATE_OR_PROHIBITED_DISPATCH` and `NATIVE_DISPATCH_REJECTED`, and with a changed request it records `DISPUTED` with `LATE_OR_PROHIBITED_DISPATCH`, `NATIVE_ARGUMENT_MISMATCH` and `NATIVE_DISPATCH_REJECTED`. These rules apply after native-request equality; an accepted acknowledgement has no power to excuse changed arguments.

If the occurrence expired, stopped or became dependency-blocked after permission, an observed native attempt is still retained under the same safe-not-sent versus possibly-sent distinction. A possibly sent attempt produces `DISPUTED` with `LATE_OR_PROHIBITED_DISPATCH` and never reopens its route. A `PERMITTED` occurrence becomes `OUTCOME_UNKNOWN`; a `BLOCKED_DISPUTE` occurrence stays blocked; and a completed or removed occurrence retains the dispatch without reactivation. This fact requires later effect reconciliation; the host must not discard it as an inactive-occurrence refusal. An acknowledgement records only what the connector acknowledged. `ACCEPTED` means that the connector accepted or received the request according to its stated contract. It does not establish the requested effect. Dispatch observations never settle exposure or complete an occurrence.

## LIFE-010. Effect observation

An `EFFECT_OBSERVED` event supplies native evidence, actual typed fields and collections, provider, source, record type, stable provider-native operation identity, observation time, event time where known, an attributed native request and the budget input needed to reconcile exposure. A governed branch also supplies the complete permit, exact dispatch binding and a nullable completion-authorization record. For both branches, `clock_revision` is null exactly when `budget_inputs` is empty. Otherwise it identifies the latest retained available lifecycle clock for the registry clock source. A missing, stale or wrongly sourced revision is `CLOCK_INVALID`. For a governed branch, `EFFECT_ESTABLISHED` and `OUTCOME_UNKNOWN` evidence use the active step's exact effect provider/source/record-type triple, while `NO_EFFECT_ESTABLISHED` uses its exact no-effect triple. The selected triple must equal the native-evidence fields before any result field is interpreted. This binding applies to authority-only and budget-backed occurrences. The consumer also checks instance, occurrence, proposal, permit and dispatch. The evidence's `attributed_request` equals the exact native request retained in that dispatch record, projected with work class, instance, occurrence, step, interface, operation and fields. Its `native_request_digest` equals `digest("native-request",attributed_request)`. The governed outcome copies the dispatch record's exact `dispatch_attempt_digest` as well as its complete `dispatch_digest`. This binding permits the consumer to retain evidence for changed arguments that may have reached the connector. It does not make those arguments authorized. A governed effect whose permit is absent from admitted state is `PREREQUISITE_MISSING`; a permit present in state with a dispatch binding for another permit or occurrence is `BINDING_MISMATCH`.

The evidence timeline is explicit. For every budget-backed effect, `native_evidence.observed_at` is no later than the selected latest retained registry clock; a later observation is `CLOCK_INVALID` and leaves governed state unchanged so the host can retain and resubmit the raw evidence after supplying a current clock. For a governed `OUTCOME_UNKNOWN` or `NO_EFFECT_ESTABLISHED` assertion, `observed_at` is no earlier than the retained dispatch attempt; an earlier assertion is `INPUT_INVALID` and cannot retain unknown status or authorize release. A temporally consistent governed `EFFECT_ESTABLISHED` record satisfies `dispatch.attempt.attempted_at <= native_evidence.event_time <= native_evidence.observed_at`. A schema-valid established effect outside that interval is retained as `UNEXPECTED`, sets `completion_mismatch:true` for budget reconciliation, blocks unsafe progression and never routes. A foreign established effect is temporally consistent when `event_time <= observed_at`; a contrary but schema-valid foreign record remains `FOREIGN` and disputed, forces `completion_mismatch:true`, and uses the anchor fallback rather than freeing capacity from its claimed event time. These mechanical comparisons do not authenticate any timestamp.

Only a retained dispatch row that may represent a connector invocation can support normal `MATCHED` or `FAILED` completion. The decision receipt for that exact dispatch event must show that the request matched the permit and that the dispatch was observed while the permit was unsuperseded, unexpired and eligible for the active occurrence. A receipt containing `NATIVE_ARGUMENT_MISMATCH`, `PERMIT_EXPIRED`, `PERMIT_SUPERSEDED` or `LATE_OR_PROHIBITED_DISPATCH` cannot support normal completion. `SENT`, `UNKNOWN`, and connector `REJECTED` attempts remain eligible when those permission conditions held; rejection is not proof that no effect occurred. A `NOT_SENT` attempt with no accepted acknowledgement cannot support normal completion. It is not a dispatch-disqualifying fact; the dispatch-disqualifying reasons are exactly the four receipt reasons named above. A `DISPUTED` dispatch row with `DISPATCH_EVIDENCE_CONFLICT` is likewise not dispatch-disqualifying, but its conflicting attempt and acknowledgement cannot support normal completion; an established effect bound to it is `UNEXPECTED` with `mismatch_reason` `UNEXPECTED_EFFECT`. Evidence attributed to a disqualified row is still retained, but an established effect is `UNEXPECTED`, disputed, reconciled conservatively and never routes. This rule applies even when the later effect fields match the originally permitted request. A timely valid dispatch remains eligible for normal completion when exact effect evidence arrives after the permit itself expires.

The completion carrier contains one `evidence_bindings` row for every declared native request field. Request names and evidence names are each unique. For an established success, `actual_fields` contains exactly the bound evidence fields, the carrier's typed status field and, for a choice, one field named by its route-label declaration. A successful `FANOUT_EXPAND` also supplies exactly the fan-out's declared collection; every other successful carrier supplies no collection. For an established declared failure, `actual_fields` contains exactly the bound evidence fields and typed status field, omits a route-label field, and supplies no collection. Every bound evidence value must equal its original permitted request value in nominal type and value for a matching completion. A dispatch request that differs from the permit, or a request-bound field or status field that is extra, missing, wrongly typed or unequal, makes the first attributable established effect `UNEXPECTED`; it is retained and disputed rather than refused. The consumer does not reach route-label interpretation for that effect. Once the permitted request fields establish a declared success on a choice step, an absent, duplicated, wrongly typed or out-of-domain route-label field produces retained `STOPPED/LABEL_INVALID` under COMP-001 instead of `UNEXPECTED`. Collection errors use the fan-out rule in LIFE-018. Carrier field names are pairwise distinct as WCD-001 requires.

The native evidence assertion has one of three statuses. `EFFECT_ESTABLISHED` requires a nonnull `event_time` and `rules_out_past_and_future_effects:false`. `OUTCOME_UNKNOWN` requires null `event_time`, empty actual-field and collection arrays, and that flag false. `NO_EFFECT_ESTABLISHED` requires null `event_time`, empty actual-field and collection arrays, and that flag true. A contrary combination is `INPUT_INVALID`. The consumer derives the outcome rather than accepting a caller-supplied classification:

| Evidence status and admitted facts | Classification | Reservation action | Work action |
|---|---|---|---|
| `OUTCOME_UNKNOWN` | `UNKNOWN` | one `SETTLE` transition with native outcome `UNKNOWN`, retaining unsettled exposure | retain occurrence as `OUTCOME_UNKNOWN`; do not route |
| `NO_EFFECT_ESTABLISHED` with exact affirmative evidence, completion authorization when the occurrence is unresolved, and a final safe attempt set | `NO_EFFECT_ESTABLISHED` | one `RELEASE` transition with native outcome `NO_EFFECT` when a budget applies | close an unresolved occurrence as `NO_EFFECT` and follow its failure behavior |
| `NO_EFFECT_ESTABLISHED` attributed to a changed or disqualified dispatch, or to an attempt set that is not final and safe | `UNEXPECTED` | one `RELEASE` transition with native outcome `NO_EFFECT` and `completion_mismatch:true`, which retains disputed exposure when a budget applies | retain the no-effect fact as disputed; do not close, route, or release |
| `EFFECT_ESTABLISHED`, first conclusive record, exact bindings and success value | `MATCHED` | one `SETTLE` transition with native outcome `EFFECT` | close as `SUCCEEDED` and follow the success or label route |
| `EFFECT_ESTABLISHED`, first conclusive record, exact bindings and declared failure value | `FAILED` | one `SETTLE` transition with native outcome `EFFECT` | close as `FAILED` and follow the failure behavior |
| `EFFECT_ESTABLISHED`, first conclusive record, attributable but fields or carrier value differ | `UNEXPECTED` | one `SETTLE` transition, which retains disputed exposure | retain as disputed; do not route |
| A nonidentical conclusive record for a retained provider-native operation identity, except the directional effect-after-release case below | `CONFLICTING` | one `SETTLE` transition, which retains disputed exposure | retain as disputed; block dependent active occurrences |
| A matching effect after deadline closure or instance stop, or an established effect after authorized no-effect release for the same provider-native operation identity, permit and stable dispatch attempt | `LATE_MATCHED` or `LATE_AFTER_RELEASE` | settle or retain disputed exposure as declared | retain evidence; do not rewind routing |

The derived classification and context fix the lifecycle decision disposition:

| Classification and context | Decision disposition | Work consequence |
|---|---|---|
| `DUPLICATE`, with any applicable idempotent reservation result | `OUTCOME_RETAINED` | Retain the duplicate record without repeating completion or exposure. This row has first precedence. |
| `FOREIGN`, `UNEXPECTED`, `CONFLICTING`, or `LATE_AFTER_RELEASE` | `DISPUTED` | Retain and reconcile the evidence conservatively; do not route. |
| Any other budget-backed classification whose reservation receipt decision is `EFFECT_DISPUTED` | `DISPUTED` | Retain conservative exposure and never route. A conclusive classification changes an unresolved occurrence to `BLOCKED_DISPUTE`; `UNKNOWN` leaves it `OUTCOME_UNKNOWN`; a closed occurrence and its route remain unchanged. Block affected dependent progression. |

| `FAILED`, unresolved occurrence with `failure_behavior:STOP`, and either no shared budget or a `SETTLED` receipt | `STOPPED` | Complete as failed, discharge its directly owning obligation, if any, without a join and stop the instance. |
| First `NO_EFFECT_ESTABLISHED`, unresolved occurrence with `FAILURE_EDGE`, and either no shared budget or a `RELEASED` receipt | `FAILED` | Complete as `NO_EFFECT` and apply the failure route. |

| `UNKNOWN`, with no shared budget or an `UNKNOWN` reservation receipt | `OUTCOME_RETAINED` | Keep the occurrence unresolved and retain exposure. |

A newly retained governed outcome has `disputed:true` when its classification is inherently disputed or its reservation receipt decision is `EFFECT_DISPUTED`. Otherwise, with no current conflicting fact, `MATCHED`, `FAILED`, `UNKNOWN`, `NO_EFFECT_ESTABLISHED` and `LATE_MATCHED` have `disputed:false`. An outcome disputed only by its reservation receipt has an empty conflict list. `UNEXPECTED` has `disputed:true` and an empty conflict list until another conclusive record conflicts with it. `LATE_AFTER_RELEASE` is the directional special case in which established effect evidence follows an authorized no-effect release for the same provider-native operation identity, permit and stable dispatch-attempt digest. It is selected before the general conflict rule, has `disputed:true`, and lists the earlier conclusive no-effect evidence identity; the consumer updates that earlier outcome with the late effect identity symmetrically. `CONFLICTING` has `disputed:true`. Its conflict list is the nonempty raw UTF-8 sorted set of every other retained evidence identity whose conclusive fact conflicts under either of two exact scopes: the same provider-native operation identity except for that directional `LATE_AFTER_RELEASE` case, or an effect and a no-effect conclusion bound to the same permit and stable dispatch-attempt digest. The second scope applies even when the two evidence records name different acknowledgement observations, complete dispatch digests or provider-native operation identities, because one native attempt cannot both have and not have an effect. The consumer updates the corresponding earlier outcome records to contain the symmetric conflict set and sets each such earlier outcome's `disputed` value to true. All prior-conclusion, repeated-completion and additional-effect checks for governed evidence use the same permit plus stable dispatch-attempt scope; the complete dispatch digest remains the exact provenance link for each individual observation. A `DUPLICATE` outcome inherits the disputed value and conflict set of the retained same-fact outcome. When that fact already conflicts with another fact, the new duplicate lists every evidence identity in the other fact group, and each member of that group adds the duplicate evidence identity to its sorted conflict set. This changes no completion or exposure. A first foreign effect has classification `FOREIGN`; a foreign same-fact duplicate has `DUPLICATE`; and a changed conclusive foreign fact has `CONFLICTING`. Every foreign outcome remains `disputed:true`, including its duplicate. A foreign conflict list uses the same symmetric rule. When an inherently disputed governed classification concerns an active occurrence that is not `BLOCKED_DISPUTE`, the occurrence becomes or remains `OUTCOME_UNKNOWN` and active descendants are blocked as LIFE-013 requires; a `BLOCKED_DISPUTE` occurrence remains `BLOCKED_DISPUTE`. `UNKNOWN` with a disputed budget result also leaves an occurrence that is not `BLOCKED_DISPUTE` `OUTCOME_UNKNOWN`. When a conclusive `MATCHED`, `FAILED`, or `NO_EFFECT_ESTABLISHED` classification is blocked solely by an `EFFECT_DISPUTED` budget result, an unresolved occurrence becomes `BLOCKED_DISPUTE`. When any of these disputes concerns an already completed occurrence, the completed row and its route stay unchanged; the occurrence is not recreated, but dependent active descendants and obligations become blocked. A duplicate or later unknown record does not alter an earlier completed disposition.

Evidence-identity duplicate and conflict classification precedes no-effect authorization. For one permit, distinct attempts are the unique stable `dispatch_attempt_digest` values ordered by the decision-receipt sequence that first retained each value. A no-effect assertion has a final safe attempt set only when its stable attempt digest is the last value in that order and every other distinct attempt for the permit has attempt status `NOT_SENT` with no retained `ACCEPTED` acknowledgement. An acknowledgement update for the same stable attempt does not create another attempt in this ordering. A later or otherwise possibly sent attempt prevents evidence about an earlier attempt from proving that the permitted operation as a whole cannot still take effect.

`completion_authorization` is nonnull for a first `NO_EFFECT_ESTABLISHED` assertion about an unresolved active occurrence when the dispatch request matched the permit and no dispatch-disqualifying reason applies. An earlier matching `NOT_SENT` attempt with no accepted acknowledgement does not prevent that authorization. When a later distinct attempt for the permit exists, an assertion bound to the earlier attempt lacks a final safe attempt set, so `completion_mismatch` is true with `UNEXPECTED_EFFECT`, the reservation becomes or remains disputed, and nothing completes, routes or releases. This includes an assertion whose authorization is valid but whose attempt set is not final and safe; the consumer retains that assertion as `UNEXPECTED`, and the authorization cannot close the occurrence or release exposure. The authorization is an accepted organizational-authorization evidence record whose organization equals the deployment organization and whose subject is `digest("no-effect-completion",{specification_pin,work_class_digest,instance_id,occurrence_id,permit_id,dispatch_digest,native_evidence_digest})`, where `native_evidence_digest` is `digest("native-evidence",native_evidence)`. Its raw UTF-8 sorted authorization scope contains those seven exact subject values, its recorded time is no later than `native_evidence.observed_at`, and its nonnull expiry is later than that time. A missing, pending, expired or wrongly bound record is `EVIDENCE_UNAVAILABLE` or `BINDING_MISMATCH`. A first no-effect record after the occurrence has already completed, expired or stopped carries null completion authorization and is retained without changing the completed row or route; it is `CONFLICTING` when a conclusive effect for the same permit and stable dispatch-attempt digest is already retained, regardless of complete dispatch digest or provider-native operation identity. A duplicate or contradictory no-effect record against an earlier conclusive effect also carries null completion authorization and remains retainable under the duplicate or conflict rule. A no-effect assertion attributed to a changed or otherwise disqualified dispatch carries null completion authorization and is retained as `UNEXPECTED`. This rule makes affirmative no-effect closure representable for both authority-only and budget-backed active occurrences while preventing a mismatched, disqualified, or incomplete attempt account from releasing capacity. A budget-backed transition that newly changes an `OPEN` or `UNKNOWN` reservation to `RELEASED` must separately satisfy the reservation administration rule, including for a late no-effect fact; one record does not silently replace the other.

The lifecycle determines the outcome classification before constructing a shared-budget event. It maps native assertion `EFFECT_ESTABLISHED` to `SETTLE/EFFECT`, `OUTCOME_UNKNOWN` to `SETTLE/UNKNOWN`, and `NO_EFFECT_ESTABLISHED` to `RELEASE/NO_EFFECT`, including when a changed, disqualified, or incomplete attempt account makes the lifecycle classification `UNEXPECTED`. The reservation transition then applies the prior-state table in `RESERVATION-RECORDS.md`. A first matching effect settles; a first authorized no-effect record with a final safe attempt set releases; and a first unknown record retains pending exposure. Exact or same-fact duplicates return the established reservation disposition without adding exposure. An unknown record after `SETTLED` or `RELEASED` is retained without changing that conclusion. A contradictory no-effect record after settlement and an effect after release are retained as disputed exposure rather than rejected or treated as release. This ordering prevents the raw assertion kind from erasing an earlier conclusion.

For a shared-budget occurrence, `budget_inputs` is empty exactly when the permit has no budget-revision row. Otherwise it contains exactly one registry input. Its registry digest and affected-anchor set equal the permit row, and the embedded native reservation identifier equals that row's reservation identifier. The supplied registry state, configuration and host registry bindings satisfy the same one-registry checks as proposal. Its expected revision equals the supplied current registry revision; it can be later than the permit's retained post-`RESERVE` revision because other serialized events may have committed in between. An extra registry, changed anchor set, wrong reservation or stale current revision is the corresponding schema, binding or revision refusal and leaves both states unchanged.

The lifecycle then constructs the embedded reservation native record exactly. `id`, `provider`, `source`, `evidence_ref`, `actual_fields` and `collections` copy the native evidence. `request` is the original permitted and reserved request projection. For `EFFECT`, `observed_request` is the dispatch-attributed request when every completion binding maps the actual evidence fields back to that exact request with complete declared types; it is null when any field is missing, extra, inconsistent or unprojectable. It is also null for `OUTCOME_UNKNOWN` and `NO_EFFECT_ESTABLISHED`. A null observed request on an established effect requires `completion_mismatch:true` and invokes the reservation policy's anchor-level fallback. `completion_mismatch` is true exactly when the dispatch-attributed request differs from the permit, a dispatch-disqualifying reason applies, a no-effect assertion lacks a final safe attempt set, or the lifecycle classification is `UNEXPECTED` or `CONFLICTING`. This applies to EFFECT, UNKNOWN and NO_EFFECT native outcomes. When changed native arguments or another dispatch-disqualifying fact causes the mismatch, `mismatch_reason` is `NATIVE_REQUEST_MISMATCH`; every other true mismatch uses `UNEXPECTED_EFFECT`. A false mismatch uses null. These exact values let the reservation transition distinguish the two receipt reasons without interpreting lifecycle context that its input does not contain. The mismatch forces a native record bound to changed arguments, a disqualified attempt, or an incomplete account of attempts to remain disputed even when the assertion itself is unknown or no effect, and it forces a conclusive record that conflicts under the wider lifecycle evidence identity to remain disputed even when the narrower reservation projection would otherwise look like a duplicate. For a lifecycle `DUPLICATE`, the consumer copies the retained same-fact outcome's complete embedded reservation-native record and changes only `id` and `evidence_ref` to the new evidence values. It therefore preserves `completion_mismatch`, `mismatch_reason`, `observed_request`, the original request, outcome, effect identity, occurrence time and no-effect flag exactly. A duplicate of `UNEXPECTED` or `CONFLICTING` remains completion-mismatched, and the reservation transition recognizes it as the same fact rather than inventing a second conclusion. `reservation` is the permit's retained reservation identifier; `outcome` maps `EFFECT_ESTABLISHED` to `EFFECT`, `OUTCOME_UNKNOWN` to `UNKNOWN` and `NO_EFFECT_ESTABLISHED` to `NO_EFFECT`; `effect_id` is the provider-native operation identity for `EFFECT` and null otherwise; `occurred_at` is the event time for `EFFECT` and null otherwise; and `rules_out_past_and_future_effects` copies the evidence value. The reservation event identifier is `digest("lifecycle-reservation-event",{instance_id:event.instance_id,lifecycle_event_id:event.event_id,lifecycle_event_kind:"EFFECT_OBSERVED",reservation_event_kind,registry_digest})`, where `reservation_event_kind` is `SETTLE` or `RELEASE`. Its event clock is the accepted lifecycle clock whose source equals the reservation registry configuration's `clock_source` and whose revision equals `clock_revision`, projected as `{source,status:"AVAILABLE",instant:observed_time}`. The registry request's authenticated native record digest is `digest("reservation-native-outcome",native)` under its declared provider and source. All other history and administrative fields remain the exact complete reservation input. A mismatch at any projection is `BINDING_MISMATCH`; the lifecycle cannot show one account or amount while the registry reconciles another. The reservation transition treats `completion_mismatch:true` as disputed exposure even when the provider attributes the effect to the changed dispatch request.

The single registry result and work transition commit together. An established success or declared failure can progress the graph only when the reservation receipt decision is `SETTLED`. An affirmative no-effect result can follow the declared failure behavior only when it has a final safe attempt set and the reservation receipt decision is `RELEASED`. Authority-only occurrences have no registry result and apply the corresponding lifecycle classification and attempt-set rule directly. A registry decision of `UNKNOWN` retains the active occurrence and exposure. `EFFECT_DISPUTED` makes the work decision `DISPUTED` and prevents routing regardless of the carrier classification. A reservation admission refusal makes the lifecycle event an admission refusal, so neither work nor registry state changes. An authority-only occurrence uses no budget input and applies the same effect classification without a registry transition.

A policy decision can therefore be `STOPPED` while its triggering occurrence accurately records the native success, failure, no-effect fact or expiry that preceded the stop. `completedOccurrence.disposition` has no generic stopped value.

The `EFFECT_OBSERVED` event has two closed branches while retaining one event kind. A foreign branch supplies null permit, dispatch and completion authorization, one attributed request and provider-native operation identity, and `EFFECT_ESTABLISHED` native evidence. The attributed request's work class equals the supplied definition ID, its instance equals the event instance, and its step resolves to one proposal-capable step in that definition. Its interface and operation equal that step, and its field names and types form the step's exact declared input inventory; the values may differ from any retained proposal. A foreign request outside this definition or for an undeclared or structural step is `REFERENCE_INVALID` or `BINDING_MISMATCH` and remains available to the host event log without entering governed state.

The resolved step fixes whether the foreign branch is authority-only or budget-bearing. When its declared `shared_budgets` set is empty, the event has null `reservation_id`, an empty affected-anchor set, no registry input and null `clock_revision`. When the set is nonempty, the event has one nonnull stable reservation identity, `affected_budget_anchors` equals that exact declared set, and exactly one registry input contains every named anchor and uses the same exact affected-anchor set. Null reservation identity or a missing, extra or partial anchor set is `BINDING_MISMATCH`; it cannot turn a budget-bearing operation into an authority-only effect. When the reservation is retained in the supplied registry, its retained contribution anchors also equal that declared set and the embedded histories cover it. When the reservation is unknown, the declared step set supplies the complete anchor inventory for the disputed transition; the implementation never asks the caller to guess which anchors apply. The returned lifecycle budget result and the reference host's before/after registry rows use this same exact set. Known or unknown reservation status is derived from the registry state rather than asserted by the caller.

For a budget-bearing foreign effect, the consumer constructs exactly one embedded `SETTLE/EFFECT` transition. The embedded event identifier is `digest("lifecycle-reservation-event",{instance_id:event.instance_id,lifecycle_event_id:event.event_id,lifecycle_event_kind:"EFFECT_OBSERVED",reservation_event_kind:"SETTLE",registry_digest})`. Its expected revision is the supplied current registry revision. Its clock is the accepted available lifecycle clock selected by `clock_revision`, projected as `{source,status:"AVAILABLE",instant:observed_time}`, and its source equals the registry clock source. Its administration is null. The histories and host evidence remain the complete values supplied by the registry input; authenticated records include exactly the supplied history and native payload digests under the reservation contract.

The embedded native record copies the native evidence's identity, provider, source, evidence reference, actual fields, collections, provider-native operation identity and event time; it sets outcome `EFFECT` and the no-effect flag false. Its `reservation` is the event's `reservation_id`. For a known reservation, `request` is that reservation's exact retained native request. For an unknown reservation, `request` is the event's attributed request. When the foreign record is temporally consistent, `observed_request` copies the work class, instance, occurrence, step, operation and interface from the attributed request and takes its fields through the attributed step's declared completion bindings: each bound evidence field supplies its request field, and the step's declared status field and route-label field are ignored. An actual field that is neither bound nor one of those declared fields, a missing bound field, or a field whose value does not have its declared type makes the record unprojectable, and its `observed_request` is null. For a temporally inconsistent record, `observed_request` is null. Every foreign embedded record sets `completion_mismatch:true` and `mismatch_reason:UNEXPECTED_EFFECT`, including when a known reservation's projectable observed request equals its retained request. This preserves precise partition projection while preventing a foreign effect from being treated as an authorized settlement. The registry input's embedded event must equal this projection byte for byte. A different event kind or identifier, wrong reservation reference, stale revision, clock disagreement, changed native projection, missing authenticated record, extra registry or changed affected-anchor set is the corresponding admission refusal and leaves both work and registry state unchanged.

A well-formed record for another known or unknown actuation is `FOREIGN`. It cannot discharge a current occurrence. The registry transition retains the effect as disputed exposure under its known-reservation or unknown-reservation rules and blocks every projectable partition or the anchor-level fallback fixed by the immutable policy. The work outcome retains the affected anchors and the exact reservation receipt digest. The implementation never treats the record as an authorized or completed occurrence merely because its native record or reservation is known. A foreign unknown-outcome or no-effect assertion has no exact permit basis in this branch and is `INPUT_INVALID`; a host may submit those facts through the governed branch when it can bind them to the retained permit and dispatch.

## LIFE-011. Unknown and no-effect outcomes

An `UNKNOWN` native outcome records that the effect has not been established. The occurrence remains unresolved, every unsettled reservation remains charged once and the work graph does not advance along a success route. A timeout, missing acknowledgement, permit expiry, authority revocation or scheduler stop cannot release capacity by itself.

`NO_EFFECT_ESTABLISHED` requires the affirmative evidence and release authorization declared by the work class and shared-budget policy, and its dispatch must have the final safe attempt set defined by LIFE-010. The consumer may then apply an exact `RELEASE` transition. Release removes the reserved exposure but does not make the operation successful. The work class follows its declared failure behavior. A step with `FAILURE_EDGE` records `FAILED` with reason `NO_EFFECT_ESTABLISHED`, completes the occurrence as `NO_EFFECT`, and follows that exact edge. A step with `STOP` records `STOPPED` with reason `NO_EFFECT_ESTABLISHED`, completes the occurrence as `NO_EFFECT`, and creates no successor. The implementation supplies no default release policy.

## LIFE-012. Late evidence

Evidence may arrive after a deadline expiry, scheduler stop, unknown outcome, dispatch-permit expiry or authorized release. If it exactly identifies a known permit and dispatch, the consumer retains it and reconciles shared exposure. Permit expiry closes the dispatch window; it does not close an occurrence whose native request was dispatched while the permit was valid. A matching effect for that unresolved occurrence completes and routes normally even when observed after the permit expiry. Its event time determines aggregate window membership. Evidence after a deadline or stop cannot create a new permission, erase an earlier closure, reopen completed routing, or make a withdrawn authority current.

A matching effect that arrives after deadline closure or instance stop is `LATE_MATCHED`. It can settle the historical reservation but cannot rewind the graph to the success route. When another branch stopped the instance while this occurrence remained active and was not `BLOCKED_DISPUTE`, conclusive matching evidence moves that sibling to `completed` with `late:true`, null route fields and the evidence-derived disposition in LIFE-010, and discharges its directly owning obligation, if any, without firing the join. A dependency-blocked sibling retains the evidence and remains blocked under LIFE-013 regardless of terminal instance status. An effect after an authorized release is `LATE_AFTER_RELEASE` when it has the same provider-native operation identity, governed permit and stable dispatch-attempt digest as the earlier no-effect conclusion. It remains disputed exposure, blocks the affected partitions, names the earlier no-effect evidence in its conflict list and causes that earlier record to name the late effect symmetrically. An effect with a different provider-native operation identity but the same permit and stable attempt is `CONFLICTING` under LIFE-013. In either case the release record remains part of history.

## LIFE-013. Replay

Each instance retains the event identifier, exact event digest, decision, permit or null, complete budget results, transition-state digest and transaction digest for every admitted event. The complete canonical event and response preimages live in the host event log under the retained identifier and digests; they are not duplicated inside the state checkpoint. Submitting the same event identifier and exact canonical event bytes against a state that already contains the record returns those exact historical transition fields together with the current complete state and its digest, with `replay:true`, even when the event names the historical expected state. `transition_state_digest` remains the original decision's next-state-core digest and may therefore differ from the returned current `state_digest`. The replay request contains the original registry-scoped budget inputs because they are part of the exact event; current registry states are not separate replay inputs and cannot replace the retained historical budget results. Replay creates no new receipt, reservation, dispatch, outcome or revision. Reusing the event identifier with different bytes, including changed embedded budget inputs, returns `REPLAY_CONFLICT` and leaves all states unchanged. A new event whose expected revision or digest does not match the supplied current state is refused as stale.

Native provider records carry both an evidence identity and a provider-native operation identity. Repeating exact evidence through exact event replay is idempotent. A second conclusive record with the same provider-native operation identity and different content is conflicting evidence. The consumer retains both evidence identities, places the sorted identifiers of every other conflicting record in each outcome's `conflicts_with_evidence_ids`, marks those outcomes disputed and blocks any progression that would depend on choosing one as true.

Every occurrence retains a sorted list of the predecessor operation occurrences whose effects caused its activation. The root has an empty list; sequence, choice and loop successors name their one predecessor; parallel and fan-out heads name the structural frontier that entered their pass; and a successor after a join names the sorted recursive completion frontier of that pass. When a completed occurrence becomes disputed, the consumer computes the dependency-affected set consisting of that occurrence and every transitive active or completed descendant through these predecessor lists. Every active member other than the completed disputed root becomes `BLOCKED_DISPUTE`, and the directly owning `OPEN` obligation for any such occurrence becomes `BLOCKED`. A proposal for a blocked occurrence is `OCCURRENCE_NOT_ACTIVE`. A dispatch or unknown outcome already retained for that occurrence remains attributable. Later exact effect or affirmative no-effect evidence is admitted for reconciliation. A conclusive nondisputed result with any required `SETTLED` or `RELEASED` budget receipt is retained and reconciles exposure, but the exact occurrence remains `BLOCKED_DISPUTE` and its directly owning obligation, if any, remains `BLOCKED` while the ancestor dispute is unresolved. Its decision is `OUTCOME_RETAINED` with `DEPENDENCY_DISPUTED`, plus the classification-specific reason such as `LATE_EFFECT` or `NO_EFFECT_ESTABLISHED` when applicable. It records no route and creates no successor. Unknown or disputed reconciliation also leaves the occurrence `BLOCKED_DISPUTE`.

The consumer also protects joins that have not fired. A `DISCHARGED` obligation whose retained completion frontier intersects the dependency-affected set becomes `DISPUTED` while retaining its completion basis. This includes a branch that progressed through later operations before reaching its join. The consumer then changes every `WAITING` ancestor whose exact child-pass reference contains a newly disputed obligation to `DISPUTED` while retaining that waiting reference, and repeats this propagation outward. Such an obligation has no join-eligible frontier and cannot later become discharged under this candidate. Obligations already `JOINED` remain historical, and completed descendants and selected routes are not removed or rewound. Their active descendants are blocked through predecessor frontiers. Independent active occurrences outside the dependency-affected set remain eligible. The instance retains its prior status while blocked or disputed work remains; the explicit occurrence and obligation states show why the dependent path cannot proceed. This candidate has no general dispute-resolution transition, so clearing the ancestor dispute remains outside the profile.

Evidence identities have these exact sequence rules after event replay. A new event carrying an existing `evidence_id` with byte-identical native evidence records `OUTCOME_RETAINED/DUPLICATE`, adds no duplicate outcome or exposure because the original outcome already retains those bytes, and commits any corresponding idempotent registry receipt. Reusing that evidence ID with changed native-evidence bytes is `INPUT_INVALID`. For records with different evidence IDs, the fact projection omits only `evidence_id` and `evidence_ref`; `digest("native-evidence-fact",projection)` therefore binds provider, source, record type and digest, provider-native operation identity, attributed request and digest, assertion status, actual fields, collections, times and no-effect flag. A new evidence ID with the same fact digest is also `DUPLICATE`; the consumer appends one outcome record with classification `DUPLICATE` and the new complete native evidence but does not repeat completion or exposure. This representable duplicate rule applies to governed and foreign outcomes; the foreign record remains disputed because its first fact never established an authorized occurrence. Next, an established effect after an authorized no-effect release for the same provider-native operation identity, governed permit and stable dispatch-attempt digest is `LATE_AFTER_RELEASE`. Any other changed conclusive fact for the same provider-native operation is `CONFLICTING`. Before ordinary first-effect classification, the consumer also checks for any retained conclusive established-effect outcome for the same governed permit and stable dispatch-attempt digest. A new established effect with a different provider-native operation identity is `UNEXPECTED` additional execution unless a no-effect conclusion already exists for that stable attempt; that effect/no-effect pair is `CONFLICTING`. Either result remains disputed, runs the conservative reservation settlement path and never completes or routes the occurrence again. An `UNKNOWN` after a conclusive governed result is retained without changing the earlier conclusion. A first matching governed effect after `UNKNOWN` settles and completes normally. A no-effect record after a matched effect for the same governed permit and stable dispatch-attempt digest is `CONFLICTING` regardless of complete dispatch digest or provider-native operation identity. The complete dispatch digest remains the provenance link for each observation and does not divide conclusions about one physical attempt into separate conflict scopes. These rules apply before any attempt to complete an already closed occurrence.

## LIFE-014. Clock and deadlines

Only a `CLOCK` event can advance runtime time. It carries an exact source, revision, status, observed time and evidence digest. A proposal, dispatch or effect may name the latest accepted available revision but cannot advance it. The host submits clock events through the same serialized transition boundary as every other event. A `CLOCK` event may introduce any syntactically valid host-selected source; the source need not appear in a deadline definition. The first record for a new source may use any canonical natural revision and establishes that source's revision watermark. Its first available sample separately establishes the accepted-time baseline. Source authenticity remains the clock host boundary. A source is wrongly bound when a proposal, dispatch, effect, deadline or reservation selects a retained clock whose source does not equal the authority, permit, deadline or registry source that event must use.

After exact event replay, every new clock record, regardless of status, must use a revision strictly greater than the greatest retained revision for that source. An equal or lower revision is `CLOCK_INVALID`. This gives every retained clock row a unique `(source,revision)` key. An available record also cannot move observed time backward from the latest retained available record. An unavailable or conflicting record is retained as `CLOCK_RECORDED/CLOCK_UNAVAILABLE` and advances only the source's revision watermark; it does not replace the latest available record, establish an accepted time or trigger expiry. A stale, backward or wrongly bound clock is refused as `CLOCK_INVALID`. One admitted available clock can satisfy several deadlines for its source.

Deadline activation uses retained clocks, never a fresh time hidden inside an effect. Deployment installs each exact `initial_clocks` record as the first accepted clock for its source. For a later event, `activation_clocks` is empty when its complete structural closure would activate no deadline. Otherwise it contains, in raw UTF-8 source order, an exact copy of the latest retained available clock for every distinct source needed by the newly activated deadlines. An extra, nonlatest or altered copy is `DEPENDENCY_MISMATCH`. A required source with no retained available clock causes the triggering effect or expiry evidence to be retained and settled as applicable, but the structural closure creates no successor and the instance records `STOPPED/ACTIVATION_CLOCK_UNAVAILABLE`. This is a policy stop rather than an admission refusal that would discard established effect evidence.

The lifecycle profile uses the whole-second UTC form in WCS2-003. A successful deployment creates revision `0`, so every root deadline has `activation_revision:"0"`. An event-created successor uses the resulting work-state revision, which is the prior revision plus one and equals that event's decision sequence. For each deadline, `activation_instant` is the selected clock's observed time, `activation_clock_revision` and `activation_clock_evidence_digest` copy that record, and `due` is the exact declared absolute instant, the activation instant plus the elapsed duration, or for an ancestor declaration the anchor occurrence's `occurred_at` plus the elapsed duration, as COMPOSITION section 5.1 defines. A `CLOCK` event's newly accepted available sample is the latest retained clock used in `activation_clocks` for any successor created by that event's expiry closure. Elapsed units are fixed seconds: `SECOND=1`, `MINUTE=60`, `HOUR=3600`, and `DAY=86400`. Addition uses proleptic Gregorian UTC at whole-second precision. Overflow beyond year 9999 is `LIMIT_EXCEEDED` at deployment. During an admitted effect or clock event it retains the triggering evidence and records `STOPPED/DEADLINE_TIME_OVERFLOW` with the applicable `EFFECT` or `CLOCK` detail and a `DEADLINE` detail, but no `LIMIT` detail because no natural count bound describes the date overflow. `activation_digest` is `digest("deadline-activation",{deadline_id,occurrence_id,trigger_digest,source,activation_revision,activation_clock_revision,activation_instant,activation_clock_evidence_digest,due,boundary})`; `trigger_digest` is the root deployment-activation digest or the event digest that activates the successor. Restart verifies every field. If a successor's activation clock already satisfies its deadline, the triggering evidence is retained but no successor is created and the instance records `STOPPED/DEADLINE_ALREADY_DUE`. Root deployment handles the same condition as LIFE-003.

`AT_OR_AFTER` expires when accepted time is equal to or later than due. `AFTER` expires only when accepted time is later than due. For an available `CLOCK` event, the consumer first collects every pending deadline for that source whose predicate is satisfied and orders them by due instant, canonical occurrence bytes and deadline identifier. It marks the entire ordered set expired. A due deadline whose occurrence is `BLOCKED_DISPUTE` is evidence-only: the occurrence remains `BLOCKED_DISPUTE`, its directly owning obligation, if any, remains `BLOCKED`, and it contributes no expiry route, join or successor while the ancestor dispute remains unresolved. The consumer preflights the union of declared expiry closures only for the remaining eligible due occurrences. Each selected relationship creates its own activation; two eligible expiries that target the same proposal-capable step create two occurrences in deadline order. If any eligible expiry declares stop, any eligible closure lacks a required activation clock, any activated deadline is already due or overflows, or the union crosses a limit, the transition retains the clock, keeps dependency-blocked due occurrences and obligations blocked, moves every eligible occurrence in the original due set to completed, discharges every directly owning obligation whose expected occurrence was in that eligible due set without firing a join, creates none of the proposed structural closure and sets the instance to `STOPPED`. Non-due sibling obligations remain open or blocked with their active expected occurrences. The `DEADLINE` detail's `deadline_ids` is the raw UTF-8 sorted unique union of the original due-set IDs and every newly activated deadline ID that contributed `ACTIVATION_CLOCK_UNAVAILABLE`, `DEADLINE_ALREADY_DUE` or `DEADLINE_TIME_OVERFLOW`. Its `reasons` is the raw UTF-8 sorted unique set of every applicable one of those reasons plus `EXPIRY_STOP`; a normal expiry, including an evidence-only expiry for a dependency-blocked occurrence, has an empty set. The decision is `STOPPED` and carries `CLOCK` and `DEADLINE`; it also carries `LIMIT` exactly when a count limit failed. Otherwise all eligible closures commit atomically in due-set order and the blocked due deadlines commit their evidence-only status in the same transition. The decision is `EXPIRED`, and the instance becomes `COMPLETE` only if the resulting state has no active occurrence or unresolved obligation.

When the instance is already `STOPPED`, an available `CLOCK` event still marks every satisfied pending sibling deadline `EXPIRED`. It moves each eligible non-`BLOCKED_DISPUTE` active occurrence to `completed` with `late:true`, null route fields, and the clock evidence and time, and discharges its directly owning obligation, if any. A dependency-blocked occurrence and its directly owning obligation retain their blocked statuses under the evidence-only rule above. The event creates no expiry successor, fires no join, and leaves the instance `STOPPED`. The decision is `EXPIRED` with `CLOCK` and `DEADLINE` details and no `ROUTE` detail. A `COMPLETE` instance has no pending active-occurrence deadline; its admitted clock records `CLOCK_RECORDED` and cannot change completion.

Any terminal closure of an occurrence, including `SUCCEEDED`, `FAILED`, affirmative `NO_EFFECT`, invalid-label stop, limit stop or effect-driven stop, changes each of its pending deadlines to `DISCHARGED`. `UNKNOWN` and `UNEXPECTED` leave them pending. Expiry changes them to `EXPIRED`, and late evidence never changes that status. If another branch stops the instance, sibling deadlines remain pending and later `CLOCK` events may mark them expired for evidence retention, but they never route or reactivate work. Completion and expiry are ordered by admitted event sequence. A terminal effect committed before the expiring clock event closes the occurrence. A clock event committed first expires it. Later evidence is retained under LIFE-012 and does not rewind that route. An active occurrence's `deadline_ids` names every deadline activated for that occurrence, whatever that deadline's current status; the deadline record carries the status, so an evidence-only expiry leaves the name in place.

## LIFE-015. Completion and routing

An occurrence completes only from exact effect evidence bound to its committed permit and dispatch. A caller cannot advance work by submitting a free completion status or route label. The completion carrier in the definition identifies separate effect and no-effect provider, source and record-type triples, the status field, success and failure values, and any field that supplies an exclusive-choice label.

On matched completion, the consumer records the completed occurrence, discharges its pending deadlines and updates its directly owning obligation, if any, as COMPOSITION requires. For an ordinary success, failure, label or expiry edge, `selected_relationship_digest` is `digest("relationship",relationship)` for the exact selected record. A `FANOUT_EXPAND` success uses the construct exception in LIFE-018 and records null. These changes and any reservation settlement occur in one transition. If structural closure reaches the defined terminal and leaves no active occurrence or unresolved obligation, the instance becomes `COMPLETE`. Otherwise the consumer records the declared failure or stop. It never invents a route.

One `ROUTE` detail describes the complete finite structural closure performed by that decision. `relationship_digests` is the raw UTF-8 sorted unique set containing the direct selected relationship from each triggering operation or expiry and every explicit relationship traversed from a structural join to its successor. An implicit split-to-branch or fan-out-to-object activation contributes no relationship digest because the definition has no such relationship record. `construct_ids` is the raw UTF-8 sorted unique set of every parallel block or fan-out whose split, expansion or join the closure reaches or passes through; a closure that ends at a join that does not fire names that join's construct. An ordinary linear or choice effect therefore names its one direct relationship and no construct. An effect entering a parallel split names its direct relationship and the block. The final branch or object effect names its relationship to the join, the join's outgoing relationship when present, and the block or fan-out. Empty fan-out advance names the fan-out and the join's outgoing relationship when present. A `CLOCK` event unions the trace from all due expiries before applying the same sorts. One structural closure traverses at most 64 construct identifiers under WCD-001; the union for one clock decision contains at most the candidate's 64 parallel-block and 64 fan-out identifiers, so the closed result bound is 128. The triggering completed occurrence still retains only its own direct `selected_relationship_digest`, or null for `FANOUT_EXPAND`; the decision detail records the wider closure trace.

All obligations for one parallel or fan-out construct pass share one exact outer enclosing prefix. A branch occurrence appends its `BRANCH` segment to that prefix; an object occurrence appends its `FANOUT` segment. Region-local loop or nested-construct segments follow it. When the pass joins, the successor removes the discharged branch or fan-out segment and every region-local segment after it, retains the common outer prefix, and then appends only segments introduced by the continuing structural closure. Its predecessor list is the raw UTF-8 sorted recursive completion frontier of the obligations discharged for that pass, as COMPOSITION defines it. Static graphs that cannot establish one common prefix are `DEFINITION_INVALID`; a retained obligation set, completion frontier or occurrence path that disagrees is `STATE_INVALID` on restart.

## LIFE-016. Choice and loop decisions

An exclusive-choice label comes from the exact native effect record through the declared completion carrier. The host cannot supply a separate label. Definition admission rejects missing mappings, duplicate mappings and a label domain without one exact target for every member. A well-formed observed effect whose label is outside the admitted domain is retained and produces `STOPPED` with `LABEL_INVALID`; the consumer does not discard the native effect as malformed input.

Every loop occurrence receives a new occurrence identity and a new proposal under current authority and shared-budget state. Activation at the declared maximum is allowed. When an established effect would activate one occurrence beyond the maximum, the consumer retains the effect, records `STOPPED` with `LOOP_BOUND_REACHED` and creates no successor. A retry with the same event identity is replay, not a new occurrence.

## LIFE-017. Parallel obligations

A parallel split preflights every branch and all applicable instance and occurrence limits. It then creates the complete branch obligation set and activates every branch as one transition. If the admitted effect that reaches the split would exceed a limit, the effect remains retained, the decision is `STOPPED` with reason `LIMIT_EXCEEDED`, and zero branch occurrences or obligations are created. A join examines the retained obligations created for that exact block pass. It activates only in an eligible `ACTIVE` transition when all those obligations have status `DISCHARGED`; `BLOCKED`, `WAITING` and `DISPUTED` obligations do not satisfy the join. It does not infer obligations by counting graph nodes, agents or visible workers.

A branch failure applies the operation step's declared failure or stop behavior. It prevents new dispatch where the definition requires a stop, but it does not cancel, reverse or forget a sibling dispatch or effect. Late sibling evidence remains attributable to its exact occurrence and is retained under LIFE-012.

## LIFE-018. Frozen fan-out

A fan-out set comes from the exact native effect field declared by the completion carrier. Successful completion of a `FANOUT_EXPAND` selects the named fan-out construct rather than an ordinary success relationship; that step has no outgoing `SEQUENCE` or `LABEL` relationship. Its completed occurrence has `selected_relationship_digest:null`. The decision's `ROUTE` detail contains the fan-out construct ID and the relationship digests added by any empty-set join closure under LIFE-015. The consumer preserves the completion array's order and uses canonical typed value bytes to detect duplicate object identities. It preflights the complete set, every occurrence and obligation, and every declared limit before changing state. It then freezes the set and creates all object obligations and active occurrences atomically. If the admitted effect would exceed a limit, the effect remains retained, the decision is `STOPPED` with reason `LIMIT_EXCEEDED`, and zero fan-out occurrences or obligations are created.

The definition declares whether an empty set advances to the all-done join or stops. There is no default. The join examines only the obligations created for the frozen set and exact pass. A later source read cannot replace the set. Re-entry to the same expand step under the same exact outer enclosing prefix is excluded from this candidate and is refused as `UNSUPPORTED_FEATURE` at definition admission. First entry under a different outer prefix is a distinct context with pass `1`.

## LIFE-019. State integrity and restart

The complete work state contains the candidate pin, work-class digest, profile, role, instance, complete deployment authorization with its organizational-authorization, correspondence, source-confirmation and policy-decision evidence and their subject, record and evidence digests, the exact deployment authorization clock, revision, instance status, total activation and actuation counts, per-step counters, active and completed occurrences, obligations, proposals, permits, dispatches, outcomes, clocks, deadlines, fan-out passes, decision receipts and replay records. Step counters contain exactly one row for every proposal-capable step, sorted by step identifier. `activations` increments when an occurrence of that step is created; `actuations` increments only when its initial proposal becomes `PERMITTED`. A permit renewal increments neither counter. Totals are the exact sums. Structural steps count in neither total. Counters are persisted facts and are not reconstructed from a compacted external log. Each obligation identifier is `digest("obligation",{kind,construct_id,pass,source_occurrence_ids,branch_id,object_key,join_step_id})`. State collections use these orders: active and completed occurrences by canonical occurrence bytes; obligations by `obligation_id`; proposals by `event_id`; permits by `permit_id`; dispatches by `dispatch_digest`; outcomes by `outcome_digest`; clocks by source then numerical revision; deadlines by due instant, canonical occurrence bytes and deadline identifier; fan-out passes by fan-out identifier, numerical pass and expand occurrence identifier; receipts by numerical sequence; replays by event identifier. No two fan-out pass rows share that three-field key. Registry-scoped budget inputs and results use their one registry digest; each affected-anchor inventory sorts by anchor. Native fields and collections sort by name. Credential IDs, observation digests, receipt digests, predecessor occurrence IDs, source occurrence IDs, child-pass obligation IDs, conflict evidence IDs and other identifier sets use raw UTF-8 order. Duplicate keys in any of those inventories are invalid. Redundant identities must agree with their canonical digest preimages.

The next-state core is the next state with `receipts` and `replays` replaced by empty arrays. The consumer first hashes that core as `state_after_core_digest`, constructs and hashes the decision receipt, and appends the receipt and replay record. The replay record's `transition_state_digest` equals `state_after_core_digest`. The complete state identity projection is the resulting state with every replay record's `transaction_digest` member omitted. `state_digest` is `digest("work-state",state_identity_projection)`. The transaction digest is `digest("lifecycle-transaction",{state_before_digest,event_digest,decision_receipt_digest,state_after_core_digest,budget_results})`. The consumer writes that value into the replay record. Omitting it from the state identity projection avoids a cycle; state admission independently recomputes every retained transaction digest from its replay record. This construction binds all work facts, decisions, permits and budget results without asking a digest to include itself.

A fresh conforming process can continue from the exact returned work state, definition and required shared-budget state without process-local history. State admission recomputes the current state digest, every self-contained record digest, collection order, counter sum, link equality and lifecycle transaction from its retained digest commitments. It does not reconstruct a historical state-core preimage that is no longer present. Exact replay supplies the historical event again, allowing its event and proposal digests to be recomputed before the retained result is returned.

Restart admission applies a finite invariant set. State revision equals both receipt and replay counts; receipt sequences are contiguous from one; and each receipt pairs with exactly one replay through equal event and decision digests. Active and completed occurrence identities are disjoint. Per-step activation counters equal the retained active-plus-completed occurrence count; actuation counters equal `PERMITTED` proposal records whose `prior_permit_digest` is null; and totals equal their per-step sums. A proposal record with a nonnull prior permit names the immediately preceding permit for the same occurrence; its successful new permit names that prior permit as superseded. For each occurrence, retained permits form one finite linear chain rooted at the one initial permit. Every permit has at most one immediate successor. While an occurrence is `PERMITTED`, exactly one permit is the unsuperseded head. A fork, cycle, second root, missing predecessor or several heads is `STATE_INVALID`. No superseded permit is dispatchable. Every proposal, permit, dispatch and governed outcome forms a complete forward and reverse link chain; every permit's registry fields equal its retained proposal budget result; every deadline names one retained occurrence; every active occurrence's `deadline_ids` equals the raw UTF-8 sorted identifiers of the deadlines declared for its step, each with a retained deadline record for that occurrence in any status; and every completed occurrence's evidence and selected relationship exist when its disposition requires them. Each permit's complete authority result hashes to `authority_result_digest`; its authority evidence digest agrees; its authority-act bases are the exact sorted projection of every selected act digest and complete act preimage. Each permit has exactly the prior-effect and satisfied-separation bases required by its active step at proposal time. Every prior-effect basis resolves through the retained predecessor graph to the exact source permit, governed `MATCHED` outcome, native evidence and typed value. A source outcome that is now disputed remains a valid historical basis only when LIFE-013's dependency-dispute consequences are present; later conflict does not rewrite the earlier permit. Every separation basis resolves to the exact current and prior complete authority-act bases, the prior basis also resolves on the source outcome's permit, and the two nested act actor identifiers are distinct. A `SEPARATION` decision detail exists only on the corresponding `WITHHELD/SEPARATION_VIOLATED` proposal; its complete readiness result hashes to that proposal and receipt's authority-result digest, contains its current act digest, and its self-verifying prior and current act bases expose equal actor identifiers. Candidate pin, work class, profile, role and instance agree throughout all records. A disputed outcome has `disputed:true`; a record with nonempty conflict identifiers is disputed and every named conflicting evidence record exists; a non-disputed matched outcome has no conflict identifiers.

Obligation admission checks each closed variant and its graph context. `OPEN` names one current active occurrence other than `BLOCKED_DISPUTE`; `BLOCKED` names one exact `BLOCKED_DISPUTE` occurrence; and that occurrence belongs directly to the obligation's branch or object region. `WAITING` names one existing unique child pass with the exact kind, construct, pass, common outer enclosing prefix and complete obligation inventory; at least one child is not `JOINED`; and no chain of waiting references cycles. `DISCHARGED` and `JOINED` retain a valid direct or completed-child-pass basis and its exact recursive completion frontier. A completion-based `DISPUTED` obligation retains a valid former discharge basis whose frontier intersects the dependency-affected set of at least one retained completed occurrence with disputed conclusive evidence; restart recomputes each such set from predecessor lists under LIFE-013. A retained completed occurrence has disputed conclusive evidence when any retained governed outcome bound to its permit is disputed and asserts `EFFECT_ESTABLISHED` or `NO_EFFECT_ESTABLISHED`, including an `UNEXPECTED`, `CONFLICTING` or `LATE_AFTER_RELEASE` outcome and an outcome disputed by its reservation receipt. That outcome need not be the record that completed the occurrence. A waiting-based `DISPUTED` obligation retains an exact child-pass reference containing at least one transitively `DISPUTED` obligation. No `DISPUTED` obligation is join-eligible. If an `ACTIVE` state contains a pass whose complete obligation inventory is `DISCHARGED`, that checkpoint is invalid because the eligible join should have fired atomically. A `STOPPED` state may contain an all-`DISCHARGED`, not-`JOINED` pass only when the retained stop decision and the direct completion bases prove that the join was suppressed by branch or object stop, stopped-instance late evidence, or fixed-point preflight failure. The same rule applies when that pass has no waiting parent. A `JOINED` obligation is historical and is not rewritten when a later dispute blocks descendants.

`ACTIVE` state has at least one active occurrence or unresolved obligation with status `OPEN`, `BLOCKED`, `WAITING` or `DISPUTED`. `COMPLETE` has no active occurrence or unresolved obligation and has a terminal closure. `STOPPED` has a retained stop decision. Every occurrence predecessor set, obligation source set and completion frontier obeys the declared 4096 bound. The consumer refuses any changed digest, missing record, broken binding, status violation or noncanonical ordering as `STATE_INVALID` before applying the next event.

`maximum_proposals` is a nonnegative integer no greater than 4096. Its retained count is the number of decision receipts whose `event_kind` is `PROPOSE`, including authority or budget withholding and an actuation-limit stop; the corresponding replay count is identical. It does not depend on whether a proposal record or permit was created. Exact replay, state identity and event-to-occurrence binding are checked before this ceiling; the ceiling is checked before current authority, clock, observation, budget or actuation evaluation. A new proposal when that count equals the limit returns `LIMIT_EXCEEDED` without changing work or budget state. Dispatch observations, effect observations and clocks for existing work remain admissible after that point, so the limit cannot strand a permit, reservation, unknown outcome or late effect. Restart admission recomputes this count from the retained decision receipts and rejects disagreement with the definition or replay inventory as `STATE_INVALID`. The append-only evidence histories have no policy ceiling in this candidate. A host resource failure while retaining them is an execution failure and does not become a governance refusal. The reference host's in-process persistence demonstrates serialization and export of complete state. Durable storage, archival evidence retention, capacity planning and crash recovery remain documented host obligations.

## LIFE-020. Host boundary

The deterministic transition assumes that the host supplies authentic deployment authorization, identities, credentials, revocation information, observations, clocks, connector records and native evidence. It also assumes that the host serializes competing deployments and events, installs one authoritative initial root for each organizational instance, persists the complete transaction before dispatch and protects event ingress. `EXTERNAL-DEPENDENCIES.md` defines the required controls, evidence formats, failure behavior and deployment checks for those facts.

The reference host first serializes installation by the exact tuple `{organization,instance_id}`. If the namespace is empty, it atomically installs the complete initial state and returns `HOST_DEPLOY/INSTALLED` with `replay:false`. Repeating the byte-identical successful deploy request and calculated initial state returns the same authoritative state digest with `replay:true`. A different candidate, definition, profile, role, deployment authorization, authorization evidence, clock input or calculated state for an occupied namespace returns `HOST_DEPLOY/INSTANCE_OCCUPIED`, names the authoritative and proposed state digests, leaves the authoritative root unchanged and has `dispatch_performed:false`. The host accepts no `step` for a state that was calculated but not installed. The in-memory host demonstrates this rule within one process. A production host must preserve the organization-and-instance namespace across restarts and coordinate it across every candidate and node that can deploy work. It may implement that serialization, and the serialization of each reservation registry, with any store that atomically rejects a write whose expected revision is stale.

The reference host exposes a closed host-commit result for the transition that precedes dispatch. `COMMITTED` binds the transaction, before and after work-state digests and before and after reservation-registry state digests. The same in-process commit retains the complete canonical request and response preimages under the admitted event identifier, event digest and transaction digest. `COMMIT_FAILED` binds the attempted transaction, the unchanged authoritative work and registry digests and an opaque host-supplied failure identifier, has `dispatch_performed:false`, and adds no authoritative event-log entry. The caller supplies that identifier with a deterministic injected failure, and the reference host echoes it as `failure_reference`; the contract does not assign it a digest domain or interpret its text. On failure, `authoritative_state_digest` equals `state_before_digest` and each authoritative registry digest equals its corresponding before digest. Host budget arrays sort by reservation-registry digest and record the exact affected anchor set. The host compares caller-supplied work and registry state with its authoritative root while holding the same lock used for evaluation and commit. It constructs one immutable next root, including its event-log entry, and swaps that root once; an injected failure before the swap leaves the entire prior root in force. A refusal, exception or failed commit cannot leave the serialization queue unusable. Host deployment and commit results belong to `REFERENCE_SINGLE_PROCESS_CONTENTION`; neither is a ninth adapter operation or a policy decision. A conformance report may qualify the pure semantic transition and the reference host's single-process installation, serialization and in-process event-log retention. It cannot infer truthful observations, authentic people, durable production storage, correct native connector behavior or distributed coordination from those tests. These boundaries state where a deployment must connect its own controls to the contract.
