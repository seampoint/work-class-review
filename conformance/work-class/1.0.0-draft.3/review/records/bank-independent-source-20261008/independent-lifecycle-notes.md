# Independent lifecycle construction

The constructor reads the frozen lifecycle inputs and draft-3 normative contract. It imports only the newly authored independent common and authority modules. It does not read consumers, the original complete bank cases, existing expectations, runtime outputs or result-derived builders.

The frozen lifecycle scope contains three LINEAR deployments and nineteen step events. Every definition has one proposal-capable operation and one SEQUENCE relationship to a terminal. Every operation selects STOP_RETAIN completion and a SOURCE_REQUIREMENTS dispatch gate. No lifecycle case selects shared budgets, exclusive keys, deadlines, choices, loops, fan-out, parallel obligations, prior-effect bindings, actor separation, recovery, or nonempty referral routes. The constructor asserts those scope constraints.

Deployment follows LIFE-003 and LIFE-004. It recomputes definition, authorization-subject, evidence, complete authorization, occurrence and activation digests. It checks accepted evidence, deployment clock applicability, exact source obligations, complete readback provision-path coverage, nested correspondence review binding, source-confirmation subject, policy-decision subject and organization scope. It creates the full empty histories required by the selected dispatch and completion profiles.

Prior states are validated by reconstruction. The constructor selects the matching frozen deployment or preceding exact frozen runtime event, reconstructs its result recursively, and compares that complete source-derived state with the legitimate supplied prior state. A supplied prior state cannot serve as the constructor's unverified successor template. Historical authority, flow and holdings bases are reevaluated by the independent authority module.

CLOCK construction follows LIFE-014. PROPOSE construction follows LIFE-007 and LIFE-008, including the exact authority projection, accepted clock, executor binding, selected complete authority acts, authority basis, finite permit expiry and actuation counters. Dispatch authorization follows OBSERVATIONS-AND-DISPATCH sections 5 and 6, independent-decision AUTH-008 and LIFE-009B, HOLD-007, and FLOW-006. The source, holdings and flow vectors are derived from admitted bodies. The submitted fence must equal that independent derivation. Leaf clocks, observations and evaluation points may refresh under AUTH-008; other leaf bytes remain immutable.

DISPATCH_OBSERVED follows LIFE-009 with the exact retained authorization, connector binding, request digest, stable attempt digest and timely SENT/NONE combination selected by the frozen inputs. EFFECT_OBSERVED follows LIFE-010 and COMPLETION-AND-REFERRALS: exact attributed request, complete request-bound fields, provider event and timestamp identities, constant fields, typed generated fields, and declared success. Successful completion retains the full source event and traverses the single declared terminal relationship.

Receipt and state construction follows Specification WCS2-002 and LIFE-019. The next-state core uses the work-state-core domain; decision receipt, replay, state identity and transaction digests use their separate declared domains. The receipt retains the referenced permit for authorization, dispatch and effect events, while those transitions return no newly created permit.

Case C3-BANK-024 changes generated provider disposition and warning values. These fields carry provider output and have declared types without a preknown equality constant. Its unchanged declared success and all exact bindings therefore support MATCHED completion. Case C3-BANK-054 supplies the initial filing's complete attributed request against the amendment's retained permit and dispatch. The request identity mismatch requires BINDING_MISMATCH and preserves the complete supplied work state.

This module constructs only the closed scope selected by these twenty-two frozen inputs. It does not claim to implement a general lifecycle consumer, authenticate provider truth, establish external execution, or prove source fidelity.

Verification used `python3 -B -u` to load every frozen deploy/step input, call `lifecycle(input, operation)`, and validate the complete output through the normative lifecycle schema's deployResult, stepResult or statefulRefusal definition. All twenty-two constructions and schema checks passed: three DEPLOYED results, eighteen admitted STEP results and one unchanged-state BINDING_MISMATCH refusal. This check read no original expected result or consumer output. The module imports the common BASE, so explicit frozen-input root selection follows BANK_ORACLE_INPUT_ROOT; contract and vendor root selection remain in the common module.
