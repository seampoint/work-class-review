# Permission holdings component, provisional source revision1

Status: fictional development source, not adopted or industry reviewed. This packet selects bounded permission-registry mechanics. It does not select a successor bank filing policy.

## Original provisioning example

A fictional finance organization uses one authoritative permission registry across participating work classes. Employee042 receives Vendor Master Maintenance through one class on September1. On September10 a second class with a different valid human administrator requests AP Payment Release for the same canonical employee. Those permissions are incompatible for the same actor. Each administrator may issue the individual kind of permission, but the second current grant must be withheld while the first is active. Changing class, approver, instance or account alias cannot create a separate policy inventory. A separately authorized exact revoke may end the first holding; a new immutable grant may then establish the second. Historical replay must not restore the revoked holding.

This example adapts Quinn Snell's recorded provisioning feedback. It selects exact incompatible pairs only. Prerequisites and approved exceptions remain separate requirements outside this component. Its fictional dates, actor identifiers, registry and administrator evidence are fixture facts, not reviewer testimony.

## Selected component rules

1. One immutable configuration names principal, authoritative registry, policy revision, permission catalogue, exact incompatible pairs, administration role, identity namespace and revision, provider, source, protected channel and clock source. The host resolves canonical actors and authenticates this selection. Exact strings do not prove that unequal aliases represent distinct people.
2. Initialization imports the complete current inventory under an available snapshot clock, authenticated human administration and a protected complete-inventory assertion. No imported grant may be inactive, duplicated or incompatible. Hashes and caller lists do not establish completeness themselves.
3. Every fresh initialize, grant or revoke requires exact accepted current HUMAN administration and its authenticated canonical return. Retain the complete designation, act, return and host evidence. Historical administration is evaluated at its original event instant.
4. Each immutable grant names its actor, catalogue permission, inclusive start and nullable exclusive end. Grant identifiers cannot be reused after revocation or expiry. An already held permission records a no-op without extension. An incompatible permission records withholding. Exact revocation names the old grant, actor and permission; an inactive old target records a no-op and cannot remove a later distinct grant.
5. Reconstruct the complete reachable history before fresh decisions. Preserve every event, administration preimage, receipt, digest and revision. Expected revision makes concurrent conflicting grants one ordered transition. Admission failures leave the supplied state unchanged; admitted no-op and withholding decisions advance revision.
6. Exact replay compares complete event and host evidence before fresh revision, clock, administration and capacity. Return the historical receipt with the current complete state. Changed bytes under the same event identifier refuse. Present readers require separate current host authorization.
7. The finite profile supports64 permissions,128 pairs,256 retained grants,64 retained events including initialization,32 requirements and8 supplied registry bases. At grant capacity, decisions adding no grant may record if event space remains. At event capacity, exact replay and historical export remain available; fresh mutations refuse and fresh authority or commitment withholds. No pruning or implicit migration is selected. Standalone16MiB input does not relax existing authority or leaf byte limits.
8. Generic fictional work uses APPLY_WORK for its actual executor. A separate generic review exercise may expressly require REVIEW_WORK for the exact admitted gate actor. These are mechanical examples independent of the bank's pending preparation and reviewer policy. Permission satisfies only that declared condition; it grants no business authority, approval or exception.
9. At proposal and fresh dispatch, supply the complete latest authoritative registry basis at the exact query instant. Missing, unavailable, conflicting, stale, expired, revoked or exhausted permission evidence cannot establish current permission. Historical administration or a formerly successful result is not a current permission snapshot.
10. Dispatch uses the complete source-requirements gate and an exact derived holdings row containing requirement, configuration and state digests, revision, actor, permission, grant and exclusive end. Bind the whole row to the exact invocation and authorization scope. Clip expiry by every finite grant end. An intervening registry decision requires fresh authorization; time-based expiry blocks commitment without a new registry event.
11. Native conditional acceptance is the commitment point. One process-local demonstration orders every demonstrated permission writer and exact native stub invocation under one coordinator. Retain the unique invocation intent before invocation. Failure before retention creates no invocation. A retained but not invoked intent is pending; possible acceptance followed by failure is uncertain and cannot be blindly reinvoked. Exact retry or restart returns retained pending/uncertain evidence for protected reconciliation.
12. Detailed states, conflicts, receipts, replay responses and audit records remain protected. A public denial reveals only refusal and OPERATION_NOT_ALLOWED. Host authentication, truthful latest-state selection, complete writer participation, durable custody, distributed recovery, retention policy and actual provider integration remain host obligations.
