## Implementation-profile choices, distinct from inherited business policy

The protected host selects one finite principal-wide registry and configuration, authenticates complete source classifications and current reader/access authority, and admits every actual input before it becomes reachable. Creation establishes an empty dormant context; the original prompt, work trigger and selection enter through authorized READ or IMPORT. A caller's empty inventory does not establish independence. Materialization requires an activated context. Every read or import unions complete origins and restrictions before possible exposure and records a stable logical intent plus a unique claim. Summaries, handoffs, old artifacts and compacted or restarted work retain the current sending context's complete restrictions.

Each native operation has exactly one immediate custody recipient. The selected deployment must reject missing flow declarations, alternate credentials, undeclared redirects and onward chains. The guarantee ends at that first transfer. Every evaluator, connector, reviewer, external log and audit/export route needs its own admission. Registry responses require separate current response-reader authority and retain no historical substitute for that authority. Detailed diagnostics stay protected. The exact public transport response is `Unable to process this request.` with no trailing newline, produced only from an independently admitted original request and immutable host constant.

All participating access, source, context, recipient, policy, release and withdrawal writers join the protected coordinator through first possible exposure. A fresh denial changes no state, claim or release. Before an atomic claim commit, a fresh authorized attempt remains possible. After that commit, even without observed invocation, the claim and intent remain POSSIBLE_EXPOSURE and any release remains consumed. The first profile defines no automatic same-intent recovery, retry with a new claim, rollback or reset after later proof of no exposure. Protected referral and an explicit later recovery policy are required. A new release alone does not authorize retrying the unresolved original intent. This is a conservative availability cost selected for the first implementation profile; it supersedes any revision 1 recovery reading that inferred automatic retry from a NOT_SENT, REJECTED or no-exposure observation.

The fixed profile bounds are 64 catalogue restrictions, 16 contexts, 64 artifacts, 64 origins per context, 128 events and 128 claims. Every claim consumes an event and creation consumes a nonclaim event, so the independent 128-claim boundary is unreachable before the event boundary in a valid history. Histories are not pruned, migrated or reset to create capacity. Exhaustion preserves protected replay and export while withholding fresh work.

The bank reporting restriction remains nonreleasable to the customer. No human act, model result, policy row or compensation release creates a SAR exception. The independently prepared customer message retains the existing assessment component's exact six native fields, five content criteria, one mandatory human review, current contact authority and zero attachments. These content and contact checks remain distinct from flow admission. A protected reporting-derived work trigger, selection or handoff cannot select the clean customer route.

The inherited six-role read/purpose matrix must be encoded by independently authorized ordinary access and transfer envelopes. Registry labels do not infer business-role entitlement. A newly signed grant for an otherwise prohibited role is a source-policy violation, not a generic registry inference. Complete bank filing, calendar, preparation-permission and permission-holdings behavior remains the separately selected bank package.

## 03. Reads and inherited restrictions

Every mediated read records the exact provider, source, record kind, immutable record identity, revision, content identity, bank/case scope, purpose, receiving context and applicable restrictions. The host selects and authenticates these records. An agent's claim that content is public, harmless or already known cannot replace that evidence.

The proposed component uses a conservative whole-context rule: all restrictions from admitted reads and imports accumulate in the receiving context, and every output from that context inherits the complete set. This is an explicit design selection beyond bank revision1's general inheritance requirement. It can block a harmless sentence produced after an unrelated protected read. No attempt is made to infer which words were influenced by which input.

The host records the restriction before any source content, partial result, existence-sensitive failure or tool state becomes reachable. If delivery may have occurred, the context keeps the restriction. A failed read must not leave a context described as unrestricted when it might have received protected content. A source ceiling or access failure prevents delivery; it does not invite a lower-labelled retry with the same protected material.

Summaries, answers, copied files, handoff instructions, tool arguments and derived artifacts keep the producer's full restrictions and root provenance. Compaction does not reset them. A receiving agent or newly created conversation inherits them before receiving the material. Deleting visible labels, paraphrasing a record or asking another agent to send it changes no disclosure authority. Revoking read access later also does not remove information already received.

An artifact retains its exact content identity, producer context and inherited origins. Outgoing use also considers the sender's current context restrictions, so an older unrestricted artifact cannot be used to bypass a later protected read in that same context. This last rule is a provisional conservative choice. A genuinely independent receiving context may use an independently admitted artifact only when the host establishes that artifact's complete origin and the receiving context's eligibility.

## 04. Separate customer context and permitted message

The Customer Communication Agent operates in a separately admitted context. Its initial prompt, memories, transcripts, tools, retrieval sources, indexes, caches, imported files and restored state must exclude protected reporting information. The host establishes that exclusion from protected records of actual delivery and reachable state. A new conversation or an agent-supplied empty history is insufficient. This source makes no claim that a human or an external model provider has forgotten earlier information.

The customer context receives only independently authorized transaction and directory facts for customer-074. It may ask that customer, through the authenticated bank portal, for invoices and the business purpose of the three underlying transfers. Customer request MRB-MESSAGE-074-01 remains the business identity from bank revision1. The exact recipient, authenticated destination, subject, body, empty attachment inventory, facts revision and content rules belong to the reviewed request. No report-derived message or packet from a reporting context can be relabelled as independent facts, even if its visible text matches a transaction-provider record.

The separate customer reviewer approves the exact message and its retained content assessment. Current recipient/contact authority and the empty-attachment condition remain independent requirements. The message must not assert or imply that a SAR was considered, drafted, filed, rejected or accepted, threaten prosecution or invent an account restriction. Content review may be wrong. Its approval supplies neither reporting access nor release authority, and a model leakage judgment supplies neither.

This bank component selects no customer release of MRB-REPORTING-074. Even an authentic human act described as declassification cannot authorize that prohibited customer path. The generic positive release example is a separate fictional compensation source. It does not create a bank exception. Filing to a regulator and exceptional law-enforcement disclosure remain separately governed work outside this component; this draft grants no such disclosure permission.

Customer communication can proceed while filing is unresolved when its own independently sourced facts, authority, review and current conditions remain valid. A synthetic portal acceptance would establish only its declared send result. It would not establish customer reading, a response, semantic nonleakage or lawful disclosure.

A current read or outgoing decision depends on the complete relevant writer inventory, exact current context, policy, recipient and source identities. A concurrent read that adds reporting restrictions invalidates a previously prepared customer send from that context. An entitlement change ordered before acceptance prevents the prohibited disclosure. A change ordered afterward cannot recall information already accepted; historical evidence remains retained. Unknown delivery or send results retain their restrictions and intent rather than becoming proof that nothing happened.

Detailed internal refusals, receipts, audit records, collision responses and escalation evidence use protected reporting routes. A customer-facing failure provides no detailed reporting reason or reporting-existence information. Exact public response bytes are a later contract choice. This source does not claim protection against every timing, inference or covert channel.
