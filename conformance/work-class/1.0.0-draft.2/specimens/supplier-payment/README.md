# Supplier bank-change and invoice-payment specimen

Status: `CONTRACT_DERIVED_CROSS_LANGUAGE_VERIFIED_NON_NORMATIVE`.

This non-normative specimen applies candidate `seampoint.work-class/1.0.0-draft.2` at the `candidate_pin` in `scenarios/expectations.json` to a synthetic supplier-payment policy. It was constructed from the normative contract without reading either draft-2 implementation or its output, then checked after the independent Python checkpoint against both implementations. It is application evidence, not a new normative rule, an implementation qualification, or a claim about a production payment system.

The work class changes a supplier's destination account and then pays an invoice. Native evidence that the first operation changed `supplier-17` to `acct-new` supplies two exact prior-effect values for the payment proposal. The payment permit also retains the confirmation actor and payment-release actor, whose identifiers must differ. These bindings survive restart because the complete prior-effect and selected authority-act bases are in the work state and permit.

The shared budget counts committed and unsettled payments for each supplier during a rolling 24-hour window. Its complete initial history contains 800 USD for `supplier-17`; the limit is 1,000 USD. Two clients independently calculate 150 USD reservations against revision 1. A serialized host can commit only one. The other request is stale against revision 2. A new event against revision 2 is admitted as a policy withholding because 800 + 150 + 150 equals 1,100.

`valid-trace/requests.jsonl` is the executable success trace. It deploys the instance, records the clock, changes the supplier destination, establishes the master-data effect, reserves 150 USD, records dispatch and acknowledgement, retains an unknown payment result, accepts later matching effect evidence, settles the reservation, and completes the instance. Both adapters reproduce `valid-trace/results-derived.jsonl` byte for byte, including when each request is submitted to a fresh adapter process.

`scenarios/requests.jsonl` contains exact adapter requests for the proposal, authority, prior-effect, dispatch, uncertainty, settlement, unexpected-effect and replay variants. Both adapters agree byte for byte, and all pure-adapter assertions pass the reusable verifier. `host/commit-failure-case.json` contains the separate reference-host input and expected result for a failure before the authoritative-root swap. `contention/requests.json` groups the two clients' initial requests, the stale second request and its new-event retry. Both single-process reference hosts produce one commit under contention, refuse the stale second request, preserve the stale instance state, and match the commit-failure result exactly.

`restart/` contains complete checkpoints after deployment, master change, the atomic payment proposal-permit-reservation transition, dispatch, unknown evidence and settlement. Proposal admission and permit creation are one transition, so there is no distinct intermediate state between them. `restart/checkpoints.json` binds each file to its exact work-state or reservation-state digest.

`readback-derived.json` accounts for every work-class leaf. `correspondence-record.json` maps the seven synthetic source obligations to exact work-class paths. Deployment under LIFE-003 (amendment batch, 2026-09-13) requires an accepted correspondence review, source confirmation and policy decision, so the nested review and both acts are labelled synthetic proxy records (`synthetic:specimen-proxy-*`); no person has reviewed this correspondence, and the organizational authorization evidence is synthetic as well.
