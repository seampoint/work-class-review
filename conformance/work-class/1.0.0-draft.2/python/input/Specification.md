# Work-class specification: deterministic governance for bounded work

Identity: `seampoint.work-class/1.0.0-draft.2`. Status: DRAFT_NOT_ADOPTED, APPARATUS_ONLY. This independent private candidate defines the shared contract for deterministic governance of bounded work. A document in this directory does not establish a production deployment. The maintained historical candidates keep their original identities and results.

## Contract and supported roles

This specification states rules directly. Language of Work, Constraint Calculus, Workbench and Neo implementation code are not required to implement it. Source mappings explain origins; they do not import unstated requirements. Normative prose governs meaning, and disagreement with a schema or frozen expected result blocks qualification.

The candidate distribution is the complete file set named in `contract-manifest.json`. The manifest records identity, draft status and sorted relative file paths with raw SHA-256 hashes. It excludes itself, worked examples, suite, implementations and reports. Every manifest-listed file except `README.md` is normative; `README.md` is the informative index and adds no requirement. The manifest's raw byte hash identifies one exact candidate. No record may incorporate its own digest. Source identifiers and schema identifiers are inert; neither authorizes network or filesystem lookup. Only the bundled, closed schema graph is available.

Roles are independently reported. `AGGREGATE_EVALUATOR` qualifies aggregate judgments; `AUTHORITY_EVALUATOR` qualifies application of a grant to an operation; `SHARED_BUDGET_TRANSITIONS` qualifies returned reservation states; `LINEAR_WORK_RUNTIME`, `CHOICE_LOOP_RUNTIME`, `DEADLINE_RUNTIME` and `PARALLEL_FANOUT_RUNTIME` qualify their state machines; `REFERENCE_SINGLE_PROCESS_CONTENTION` qualifies serialized single-process access; and `REVIEW_EVIDENCE` qualifies mechanical evidence checks. Passing a role does not qualify a production host. Unsupported operations and profile combinations must be refused and omitted from capabilities.

The existing eight adapter operation names remain, with a new protocol identity. The protocol and each subsystem document define their supported input branches. `deploy`, `step` and `check-evidence` are supported for the included profiles. `LIFECYCLE.md` joins proposal authority, shared reservations, dispatch observations, effect evidence and graph progression. No adapter may synthesize omitted business requirements.

## WCS2-001. Restricted canonical JSON

Policy artifact bytes are UTF-8 JSON without a byte-order mark, duplicate map keys, invalid UTF-8, lone surrogate code points, JSON number tokens or nonfinite values. JSON null, Booleans, strings, lists and maps are permitted. Numerical quantities and counts are strings in the grammars below. Decode duplicate keys before map construction; a parser that silently keeps one value is not conforming. Unicode normalization is forbidden.

Canonical serialization is the number-free RFC 8785 subset, defined completely here: no whitespace; map keys ordered by their UTF-16 code-unit sequence; lists preserve order; quote and backslash escaped; U+0008, U+0009, U+000A, U+000C and U+000D escaped as `\b`, `\t`, `\n`, `\f` and `\r`; other U+0000 through U+001F characters use lowercase `\u00xx`; remaining scalar values appear directly as UTF-8. Slash is not escaped. Null and Boolean tokens are lowercase. Canonical set order compares complete canonical member UTF-8 bytes and forbids duplicates. Identifier sets use raw UTF-8 byte order.

Fields ending `_bytes_base64` use the standard Base64 alphabet, canonical padding and no whitespace. Reencoding decoded bytes must reproduce the string. Admission compares received artifact bytes to their canonical serialization. The incoming transport request envelope need not be canonical; protocol responses are canonical under `PROTOCOL.md`. Neither transport nor the runner may normalize artifact bytes before their admission boundary.

## WCS2-002. Digests and versions

For a role token `kind`, `digest(kind,value)` is `sha256:` followed by lowercase SHA-256 of the UTF-8 prefix `seampoint.work-class/1.0.0-draft.2/`, then `kind`, then one line-feed byte, then canonical UTF-8 value bytes. The prefix is versioned. Subsystem documents name role tokens and exact digest subjects. A digest establishes content identity, not authentication, authorship or organizational authority.

`specification_pin` is `sha256:` plus the raw SHA-256 of this candidate's exact manifest bytes. A pin supplied by an input must equal the consumer's selected manifest. Artifact and schema versions cannot be selected by ambient file discovery. Every changed frozen normative document, schema or expected result receives a new candidate identity; previous qualification remains bound to its previous identity. Development files are not frozen until a manifest exists and a freeze record identifies them.

The lifecycle and review digest kinds are `work-class-definition`, `deployment-authorization-subject`, `deployment-authorization`, `deployment-activation`, `relationship`, `occurrence`, `runtime-event`, `proposal`, `native-request`, `dispatch-native-request`, `dispatch-attempt`, `connector-binding`, `executor-binding`, `permit`, `dispatch`, `native-evidence`, `native-evidence-fact`, `no-effect-completion`, `deadline-activation`, `lifecycle-reservation-event`, `outcome`, `obligation`, `work-state-core`, `work-state`, `decision-receipt`, `lifecycle-transaction`, `boundary`, `correspondence-subject`, `correspondence` and `evidence`. The `deployment-authorization-subject` digest subject is the complete deployment-authorization record with `authorization_evidence_digest` omitted. The organizational-authorization evidence binds that subject digest. The `deployment-authorization` digest subject is the complete deployment-authorization record, including the evidence digest. The complete record can therefore bind the evidence without a cycle. A relationship digest hashes one complete relationship. The occurrence digest subject is exactly `{specification_pin,work_class_digest,instance_id,step_id,ordinal,predecessor_occurrence_ids,enclosing,object_key}`; `occurrence_id` is not part of that subject. A permit, dispatch, outcome or decision receipt contains an identifier computed from the corresponding digest kind over the complete record with that computed identifier omitted. An obligation digest subject is exactly `{kind,construct_id,pass,source_occurrence_ids,branch_id,object_key,join_step_id}`; mutable status and evidence are not part of its identity. `runtime-event` hashes the complete admitted lifecycle event and supplies `event_digest` wherever that value is retained. `proposal` separately hashes the same complete admitted `PROPOSE` event for its proposal role. `native-evidence` hashes the complete lifecycle native-evidence record. `native-evidence-fact` omits only its evidence ID and evidence reference. LIFE-009 defines the dispatch-native-request, dispatch-attempt and connector-binding subjects; LIFE-010 defines the no-effect-completion and lifecycle-reservation-event subjects; and LIFE-014 defines the deadline-activation subject. The proposal form of lifecycle-reservation-event is defined in LIFE-007. `work-state-core` hashes the complete next work state after replacing `receipts` and `replays` with empty arrays. The `work-state` subject is the complete state after omitting `transaction_digest` from every replay record; those values are verified independently. `lifecycle-transaction` hashes exactly `{state_before_digest,event_digest,decision_receipt_digest,state_after_core_digest,budget_results}`. The budget results retain the complete single-registry result where the occurrence uses shared budgets. `boundary` hashes the complete boundary record. `correspondence-subject` hashes the complete correspondence record with its nested `review` omitted; `correspondence` hashes the complete correspondence record; and `evidence` hashes any complete evidence record. LIFE-019 defines the lifecycle construction order and retained replay fields. These projections prevent circular references while retaining exact transition bindings.

References resolve only against complete explicitly supplied records or the mappings in `schema-bundle.json`. A digest-shaped identifier without its required record is not evidence. The same identifier cannot bind different records within one admitted input. A complete successor distribution includes the manifest, all named files, examples, exact suite and implementation dependencies. Installing pinned dependencies is separate from offline operation.

## WCS2-003. Exact values and time

A natural integer is `0` or a nonzero decimal digit followed by decimal digits. A nonnegative decimal has an integer part in that grammar and optionally a point followed by digits whose last digit is nonzero. There is no sign, exponent, leading zero, trailing fractional zero or binary-floating-point interpretation. Where a signed INTEGER or DECIMAL is expressly supported, a single leading minus is permitted except for negative zero. Compare and add exact base-ten mathematical values. Unit conversion is never implicit.

UTC instants use `YYYY-MM-DDTHH:MM:SSZ` or that form with exactly nine fractional digits before `Z`, as selected explicitly by the relevant temporal configuration. Years are 0001 through 9999; month/day must exist in the proleptic Gregorian calendar; hours are 00–23 and minutes/seconds 00–59. No leap seconds, offsets or 24:00 are accepted. Exact seconds and nanoseconds determine order. Temporal arithmetic must not use the host's local zone or ambient time. A subsystem that supports a narrower explicit grammar states it in its schema and prose; no string comparison replaces calendar validation.

The aggregate calendar profile pins IANA tzdb `2025a`. Consumers use the same transition data. The host may supply a clock sample only according to the declared source and precision. An unavailable clock is an explicit input, not permission to consult a machine clock.

## WCS2-004. Admission and resource boundaries

Transport failures are distinct from artifact admission and from policy decisions. A malformed event or invalid supplied state leaves governed state and reservations unchanged. A valid proposal that violates policy can return the declared policy refusal, with the record changes expressly specified by that transition. Unknown policy facts never become default permission.

Unless a subsystem explicitly imposes a different advertised bound, support is bounded to 64 definitions, 256 operations, 1024 members in an ordinary collection, 128 digits in a numerical coefficient, 64 expression levels and 4096 expression nodes. A proposal-capable step may declare at most 64 request fields, 64 prior-effect bindings and 64 prior-actor separations; its completion record may contain those 64 bound fields plus one distinct status field and one distinct route-label field. A work-class `maximum_proposals`, `maximum_activations` or `maximum_actuations` cannot exceed 4096; `maximum_active_obligations` cannot exceed 4096; and `maximum_fanout_objects` cannot exceed 1024. The closed work-class schema permits at most 425869 readback leaf or empty-collection paths, so each correspondence path inventory permits that many members and its residue inventory permits 426893 members, including the 1024 possible source obligations. Active and completed occurrences, proposals, permits, obligations, deadlines and fan-out passes have the explicit bounds in their schemas. Dispatch, outcome, clock, receipt and replay histories remain append-only so the consumer can admit evidence for existing work after new proposals stop. Input-size transport controls are reported separately and do not excuse a crash on an otherwise supported input. Resource exhaustion, timeout and implementation exceptions are execution failures, never governance results. Implementations must reject supported-shape inputs above a stated contract limit using the specified refusal or retained limit decision before evaluating or extending governed work.

## WCS2-005. Reviewable meaning

Readback renders every operative policy field with its complete canonical value. It covers nested scalar leaves and empty collections; object/list containers with descendants are represented by their descendants. Each line's `path` is one complete JSON Pointer. The pointer root is the empty string, tokens escape `~` as `~0` and `/` as `~1`, and array indices use natural-integer spelling. Lines sort by the raw UTF-8 bytes of the complete escaped pointer string, without interpreting array indices numerically or unescaping tokens for comparison. Each `value` is the WCS2-001 canonical JSON serialization of that scalar or empty collection, carried as a JSON string in the readback line. The deterministic machine rendering is not a claim to have produced or understood a faithful English paraphrase.

Correspondence accounts in both directions for declared source obligations and operative work-class provisions. The provision universe is the complete JSON-pointer leaf and empty-collection path set produced by deterministic readback of the exact work-class definition, excluding no field. A correspondence mapping binds one declared source obligation to one or more paths. The mapping source-obligation IDs plus `uncovered_source_obligation_ids` form an exact disjoint partition of the complete source-obligation inventory. The union of every mapping's paths plus `unsupported_provision_paths` covers the complete readback path set; no unsupported path may also be mapped. One provision path may support several source obligations, but each `(source_obligation_id,provision_path)` edge appears only once. Every uncovered obligation and unsupported path has exactly one residue row with its kind, exact subject, disposition and nonempty explanation. There is at most one mapping for each source obligation. The mappings sort by source obligation ID; their path sets, uncovered IDs and unsupported paths sort by raw UTF-8 order and contain no duplicates. Residue records sort first by `kind` and then by `subject`, both in raw UTF-8 order, and contain no duplicate pair.

The correspondence record binds the exact work-class digest and the work class's source ID and revision. Its nested accepted review has subject digest `digest("correspondence-subject", correspondence_without_review)`. A valid correspondence record and review have accepted status, the selected candidate pin and exact subject bindings. Pending, rejected or deferred records cannot satisfy acceptance. This mechanical check proves inventory partitioning and exact record binding. It does not prove that the English obligation was understood, that a mapped provision is faithful, or that a residue disposition is acceptable. Source confirmation, policy decisions and organizational authorization remain separate review acts. Deployment under LIFE-003 requires each of them, as distinct accepted records, together with an accepted correspondence record for the exact definition. Changed subjects require new evidence unless an explicit rule permits continued reliance.

Generic readback covers every admitted aggregate, authority and work-class definition, boundary record and evidence record. Runtime and review roles use the same exact bytes and candidate pin as the evaluator roles. The historical candidates remain available under their own identities and do not certify this candidate.

## WCS2-006. Host responsibilities

Hosts establish the real identities of people and machines, the authenticity and organizational basis of supplied records, truthful observation providers, exact projection of native invocation arguments, protected history, serialized event submission and durable commitment of returned state. A consumer checks the supplied declarations and bindings mechanically. Consistent false records can pass mechanical checks; the contract does not authenticate them through hashing.

Every evidence record that an operation relies on for a human act has an attributable return. The host retains at least the complete canonical bytes of the act as returned, their digest, the actor identifier asserted by the identity provider named in the applicable boundary record, the return channel's provider and source, the host instant of return, and those return bytes under the record's evidence reference. The record's `provenance_digest` identifies that retained return; the consumer checks its format but cannot recompute it. A detached signature over the canonical act bytes by a key that the identity provider binds to the actor satisfies the authenticity obligation. The conformance suite has no key material and cannot verify signatures, so signature format and verification remain host obligations outside this contract. The reservation administration return in RESERVATION-RECORDS is one instance of this rule.

Permission applies to the exact operation, occurrence, authority, observation revision and state evaluated. Every proposal-capable step declares a positive finite `permit_seconds` value. A successful proposal fixes the current authority and observation snapshot until the resulting permit's exclusive expiry, which may be earlier when a shared-budget policy requires it. The organization's authorization of the exact definition and candidate accepts this snapshot rule. The host commits the complete transition atomically before native dispatch and dispatches only the exact permitted request before expiry. After expiry it must obtain a new proposal and current evaluation. Every covered mutation path passes through this enforcement boundary. A reference in-memory lock does not demonstrate durable crash recovery or distributed atomicity.

Dispatch, acknowledgement and native effect are distinct facts. A timeout is not proof that an effect did not occur. Hosts retain unknown outcomes, use supported native deduplication where available, and do not redispatch blindly. Late attributable evidence may establish a past reserved effect even after scheduling stops, without granting permission for new work. Conflicting effects remain recorded and disputed. No rollback, cancellation or compensation is implied.
